# ganja-code

## Purpose

`ganja` is a terminal-first AI coding agent: a **behavioral port of [opencode](https://github.com/anomalyco/opencode) v1.18.13 to Rust**, with a ratatui TUI. Upstream's TypeScript is the *specification*, not source to translate — the port writes idiomatic Rust and matches observable behavior. The workspace is nine crates: the protocol, the permission engine, the tools and the provider wires beneath an engine that carries no terminal dependency, then a ratatui frontend, an HTTP frontend, the client that attaches to it, and the `ganja` binary that wires them together.

```sh
cargo run -- mcp                # the configured MCP servers, dialled, with the tools they lend
cargo run -- mcp login <server> # OAuth login for a remote server configured with `oauth: {}`
cargo run -- mcp add local -- npx some-server   # also: add remote --url https://…, get <name>,

cargo run -- run --continue --auto "now fix it"   # --auto allows what a headless run otherwise refuses

# The gates CI runs, in order

cargo test --workspace --doc        # nextest skips doctests, so run them beside it

! cargo tree -p ganja-core -e normal | grep -q axum      # the engine never grows an HTTP server
! cargo tree -p ganja-provider -e normal | grep -q ratatui  # and neither does a wire

#   ganja-tool     = "ganja-permission "
#   ganja-provider = "ganja-permission ganja-protocol ganja-tool "
#   ganja-core     = "ganja-permission ganja-protocol ganja-provider ganja-tool "

```

The inverted gates are deliberate: a plain `grep -c` exits non-zero on zero matches and would fail exactly when the boundary holds. Together they assert every direction that matters — the engine reaches no terminal, nothing beneath the engine reaches the engine, and the bottom crates stay leaves.

Single tests (nextest filters by name substring; `cargo test` still works and is what runs doctests):

```sh
cargo nextest run -E 'binary(golden)'                # one integration binary
cargo nextest run -E 'binary(mcp)'                   # shares golden's bun + upstream-checkout prerequisites
cargo nextest run -E 'binary(lsp)'                   # needs rust-analyzer on PATH (rustup component); hard-fails without it
cargo nextest run -p ganja-permission                # the permission engine's own tests
cargo nextest run -p ganja-provider                  # the wires, the logins and the catalog
cargo nextest run --workspace permission             # every test whose name matches "permission"
cargo nextest run -p ganja-tui snapshot_tool_error   # one snapshot test

```

Two suites need setup, and both are documented in `crates/ganja-core/tests/AGENTS.md`:

- **Golden differential** runs in the default test run (`cargo nextest run`, or `cargo test`) and **hard-fails rather than skips** when its prerequisites are missing — a green run that compared against nothing would be worthless. It needs `bun` on `PATH` and an upstream checkout with `bun install` already run, at `.omc/reference/opencode-v1.18.13` or wherever `GANJA_OPENCODE_DIR` points (CI checks it out to `upstream/`). The MCP suite (`tests/mcp.rs`) shares those prerequisites — its reference server runs on the checkout's installed `@modelcontextprotocol/sdk` — and hard-fails the same way.
- **Live provider tests** are `#[ignore]`d *and* inert unless opted in: `GANJA_LIVE_TEST=1 ANTHROPIC_API_KEY=… cargo test -p ganja-core --test live -- --ignored`.

## Environment

## Architecture

Nine crates. The load-bearing boundaries are asserted rather than trusted: nothing in the engine may reach a terminal or an HTTP server, nothing beneath the engine may reach the engine, and the two bottom crates name nothing else of ours. The graph is a DAG, not a chain — frontends sit on `ganja-core`, core on `ganja-provider` and `ganja-tool`, both of those on `ganja-permission`, while `ganja-protocol` is a leaf that core, the provider crate, the frontends and `ganja-client` consume directly and that tool and permission never touch. Every "nothing beneath may reach the engine" claim is an **allowlist** in CI rather than a `! grep ganja-core`, because a blocklist names one crate and goes quiet the day a new one appears.

**`ganja-protocol`** — the types every side of the app speaks: `Command`, `Event`, `Message`/`Part`, `ToolState`, `Usage`, and the ids that sort in creation order. Serde-derived from day one; that serialization constraint — not a trait — is what preserves the path to serving the engine over a socket and to transcripts that replay from disk. Its dependency list is `serde` and the value type a tool call's arguments arrive as, which is the whole reason it is a crate: a frontend that renders a transcript builds nothing else. A provider-run tool call is a third display-only part, `PartBody::ServerTool` — drawn by every frontend, sent by no wire, because a Tool part is what encoders replay as a function call the roster never advertised (D489). Reasoning arrives as two parts, and the split is load-bearing: `PartBody::Reasoning` is the opaque provider state a `store: false` turn hands back on its next request, while `PartBody::ReasoningText` is thinking a person can read — **display-only**, drawn by every frontend and sent by no wire, kept out of `Part::as_text` so it can never title a checkpoint or answer a copy command, counted as nothing by the context meter, and carried by no summary. Upstream opencode fuses the two into one part and replays it into the request (`session/message-v2.ts:362-376`); ganja splits them, which is what makes "display-only" a thing the type system can state. Its tag keeps the `reasoning` prefix that `REASONING_TAG` makes a forward-compatibility contract of, so a build too old to decode one still leaves storage's marker in its place rather than dropping the row without a word.

**`ganja-permission`** — a call becomes one or more patterns; the **last matching rule wins**, and **every** pattern must be allowed for the call to run unasked. Rules layer builtin defaults < the agent's < the config's < the answers a person stored. Shell "always" answers remember the *kind* of command via upstream's arity table. A subagent inherits the refusals and never the allows: nobody is watching its turn. `project.rs` rides along — which worktree this is decides where the answers are stored and what counts as outside it — and the crate's own docs own that the name is a small lie about that.

**`ganja-tool`** — `Tool` trait + `Registry::with_builtins()` (read, edit, write, glob, grep, `bash`, todowrite, webfetch, `websearch` — Exa or Parallel over one JSON-RPC POST, keys from the environment, refused politely without one — `skill`, a `SKILL.md` under one of ganja's own two homes — `<config home>/skills` and `<project root>/.ganja/skills` — or a directory `skills.paths` named, loaded into the conversation on request; **nothing foreign is discovered**, a standing ruling that leaves upstream's `~/.claude`, `~/.agents` and their walk-ups unread and one config line away, and `question`, the one tool whose whole purpose is to wait for a person), plus `task`, which the engine registers once it knows which agents this session may spawn, and the two plan doors — `plan_exit`, registered once the roster holds a build agent, and `plan_enter`, its mirror, registered once it holds a plan agent and synthesized rather than ported because upstream ships that door's description and permission vocabulary and no tool body at all (**D477**). The roster's `skill` holds no directories at all — where ganja keeps its things is not a question a tool may answer — so each of the three real frontends installs one over it holding `instruction::skill_roots`, the same value its prompt's `<available_skills>` block was composed from; a registry a *fixture* builds stays rootless, which is what keeps the golden differential comparing two agents rather than two laptops. Schemas generated from the argument structs; `FileTimes` enforces read-before-write; glob/grep run in-process on the ripgrep crates. `write` and `edit` reach the disk through a directory descriptor (`anchor.rs`), never twice through a path, so a link swapped in after the permission dialog has nothing to redirect. `watch.rs` is here too, beside the log it reports into. It depends on `ganja-permission` and on nothing else of ours — the engine is deliberately outside its graph, so a tool that seems to need the loop is a tool that needs another value in its `ToolCtx`.

**`ganja-provider`** — talking to a model vendor: the wires, the credentials they present, and the table that sizes and prices what they serve. A wire turns a `ChatRequest` into HTTP and an HTTP response back into a stream of `ProviderEvent`s; it knows nothing about sessions, tools or storage, and with the engine outside its dependency graph that is the compiler's rule rather than a convention. Anthropic Messages, OpenAI's Responses API, the chat-completions wire grok and Copilot ride, the Connect wire cursor's agent backend speaks, the fake provider, and `compat` — not another wire but the two real ones reached at an endpoint a config named, under the id it named. The cursor wire has no upstream TypeScript to port, so its spec is a recorded live probe: Connect, not bare gRPC — enveloped streams whose failures arrive as in-body EndStream frames — with the framing hand-written over the same reqwest/rustls stack, the messages riding `buffa` (pure-Rust protobuf, license-matched), and ganja's own `.proto` checked in beside its generated module under a drift test. Its Run RPC is a duplex: the request body is held open because the server generates by *asking* — a context exec whose answer is the one system-prompt channel cursor honors, and kv blob get/set served from a per-turn map — and a tool exec (shell, read, write, …) is refused on the descriptor's own throw-and-close pair so the server reads a failed tool and the turn survives (**D486**), while a kv kind outside get/set still fails the turn naming it, never hangs it; the prost/tonic fence that once reserved a separate crate for a gRPC stack retired with the reason it existed. P19 added the gateways: `openrouter` rides the Responses machinery at the vendor's own base under a plain key, every OpenAI-shaped body assumption re-derived against the vendor's reference — the API is stateless, so nothing is replayed, nothing sealed is recorded and no summary is asked for, each drop a refusal to guess recorded in the module doc — three sends now stand beside the drops: `reasoning.effort` off the /effort roster, `tool_choice: "auto"` on a roster-bearing request, and the opt-in `openrouter:*` server-tool rows (D489), whose calls come back as the display-only `ServerTool` part; `opencode` and `opencode-go` (the zen gateway's two tiers, **D488**) are one module registered twice over one key, dispatching per model to whichever of the three existing wires the catalog row's npm hint names — choosing the wire chooses the auth header, which is what the gateway's `x-api-key`-only Messages path requires — with the Messages base stripped of one `/v1` because that wire re-adds it. Everything filed under `openai` speaks Responses and asks it to seal the model's reasoning, which the transcript carries and the next request hands back; the credential picks the *backend* and what the request carries beside the bearer. Two failure channels, never a completed turn; retry only before the first byte — with one bounded exception, D475: an in-body failure that arrived before any content event is retried up to three times, since nothing rendered that a replay could duplicate; credential-travel bounds (no redirects, https-or-loopback) live here. **Auth and the catalog fold in rather than standing alone**: the auth→provider edge is one function (`reachable_in_the_clear`, the OpenAI login's redirect check) against some forty provider→auth references reaching per-provider submodule internals, and the catalog names providers by the ids `auth::storage_key` maps to disk — a boundary between any two of them would carry no invariant anyone would gate. What did *not* move is selection: `select` reads a `Config`, so it stayed in the engine over a facade that re-exports the wires.

**`ganja-core`** — the engine. No terminal dependency (CI-enforced), so it is testable headless and can later be served over a socket. It re-exports the four crates above under the module names they always had — `ganja_core::protocol`, `::permission`, `::project`, `::tool`, `::watch`, `::auth`, `::catalog` — so each split cost no caller a rewrite; new code that wants one of them alone should depend on it directly, as `ganja-cli` does for `auth login`. `ganja_core::provider` is the one facade that is not a bare re-export: the wires left and the half that reads a `Config` stayed, over a glob of what moved.

- `engine.rs` — commands in, an ordered event stream out. Delivery is **per-subscriber**: every subscriber has a bounded queue of its own — a lossless subscriber (`subscribe()`) makes the publisher wait, so backpressure lands on the turn task and never on the render loop, while a droppable one (`subscribe_droppable()`) is evicted with an observable error rather than waited for. The first subscriber inherits everything buffered since the engine was born; later ones join from registration. Every event names its session, filled from the engine's one current-session slot (minted at construction, adopted by the first prompt's row, replaced by resume, re-minted by `NewSession`); a subagent's crossing permission dialogs carry the parent's. **Root turns stay serial** — `TurnSlot`, `Busy`, "one turn at a time" all still hold — but *within* a running turn, consecutive `task` calls in one assistant step now fan out concurrently (capped by `agents.concurrency`, default four) and fan back in on completion order while parts keep call order (**D462**); the pending-reply registry (`session.rs`) lets several children hold open permission or question dialogs at once, queued rather than collided, each answered by id. `Engine::settle` polls the turn slot so a headless caller (`ganja run`) can wait for a turn's tail — its `Stop` hook included — before the process exits; `Engine::jobs()`/`shutdown_jobs()` own the background-job registry `job.rs` describes, torn down on the same exit path as `shutdown_mcp`/`shutdown_lsp`. The event stream is complete — a frontend that applies every event holds exactly what the next `ChatRequest` will carry. Two read accessors serve P14's surfaces from the same estimator compaction trusts: `context_estimate()` (tokens against the catalog window, what the status bar's meter polls) and `context_breakdown()` (the per-category split `/context` renders, computed at the request-assembly seams rather than re-derived by any frontend). Three narrow `&mut self` seams — `replace_hooks`, `replace_base_tools`, `replace_environment` — exist for exactly one caller, the `/plugin` dialog's Reload (**D474**): each swaps state a turn clones at its start, so a running turn keeps what it began with and the next one reads the reload.
- `session.rs` — the agent loop. Mark a step, ask the model, execute the tools it called, repeat until a request ends without tool calls. **Tool results are information, never control flow**: a refusal, an unknown tool, unparseable arguments or a failed tool all become error text the model reads next, and the loop continues. Only a cancel or a dead provider ends a turn early; there is no step cap. A step's calls resolve through four phases (`prepare`→`start`→`body`→`finish`) so a batch of concurrent `task` calls and an ordinary sequential call share one code path — only `body` ever leaves the turn's own thread. `crate::hook`'s nine events fire from five seams here: `PreToolUse`/`PostToolUse` bracket a call (a `PreToolUse` block, exit 2 or `permissionDecision: "deny"`, routes the same `fail_call` a denied rule does; `"allow"` skips the dialog and never overturns a stored deny, **D458**), `Notification` brackets a permission or question wait, `Stop` fires at the turn's tail before the slot releases, and `PreCompact` fires before compaction. `Turn.hooks` is inherited by `Turn::child`, so a subagent's own tool calls are gated too, and `subagent.rs` fires a child's own `SubagentStop` once its turn and its watcher both resolve.
- `hook.rs` — commands a config runs at those nine named moments (`PreToolUse`, `PostToolUse`, `UserPromptSubmit`, `Notification`, `Stop`, `SubagentStop`, `SessionStart`, `SessionEnd`, `PreCompact`), spawned under the same POSIX shell `bash` uses with the event's JSON envelope on **standard input** — this module owns its own spawn because `ShellTool`'s hard-codes `Stdio::null()`. Every hook matching one event runs concurrently and is awaited under its own timeout; exit 0 passes and its stdout is read as the documented envelope or as plain text; exit 2 blocks where blocking means something (`HookEvent::blocking` is exactly `PreToolUse`/`UserPromptSubmit`); anything else — including a timeout kill — is a non-blocking failure reported through `tracing` and the returned `Outcome`, never through a new protocol event (**D459**). A hook runs with the **user's own authority** and crosses no permission dialog — the config file it came from is the trust boundary — and never fires for another hook, by construction rather than a guard. No upstream opencode counterpart at all (**D456**); the stdin envelope omits Claude's `transcript_path` because this build's transcripts are SQLite, not JSONL (**D457**).
- `job.rs` — background shell jobs: a `bash` call started with `run_in_background: true` returns immediately and keeps running under `JobRegistry`'s own root cancellation token, a child of nothing a turn owns, so a turn's cancel never kills a background job. `bash_output` drains whatever a job wrote since the caller's last poll (one cursor per job — this port's shape has exactly one caller per job) with an optional regex `filter`; `kill_shell` ends the whole process tree. No upstream counterpart (**D454**); the `timeout` argument the tool shares with the foreground path is silently unconsulted on this branch, by design — backgrounding exists precisely so a call can outlive the foreground default (**D455**). The status bar's `N bash running` segment polls `Engine::jobs()` on every tick.
- `provider.rs` — half a module, and the half that reads a `Config`: `select`'s four-tier chain, `Selection`, `selectable`, the `Wire`/`openai_provider` dispatch that picks a backend by *kind* of credential, and the config→wire translation. The wires themselves are `ganja-provider`'s, globbed in so every path a caller already writes still resolves.
- `mcp.rs` — config-named MCP servers, dialled concurrently in the background at startup; their tools join the registry as `mcp__<server>__<tool>`, every one of them asking by default — the registry name is the one permissions, hooks and transcripts key on; a wire whose vendor refuses that spelling advertises a deterministic alias and translates the model's calls back (`provider/toolname.rs`). The original "dialled once, never reconnected" posture retired (**D463**): `Servers::reconnect` is the `/mcp` dialog's manual door for a server the dialog shows as `Failed`; `Servers::retry_once` is a bounded, spawned-and-never-awaited automatic redial — exactly one per server per session — for one whose very first dial never succeeded, run off the existing `refresh_mcp` once-per-turn-start seam; either door bumps `Servers::generation` so only the *next* turn sees revived tools. A tool result over a server's `output_limit` (bytes, default `MAX_CHARS`) is clamped through `truncate::clamp_bytes`, the same spill-file posture every other one-shot tool here uses (**D464**). A remote entry may add `oauth: {}` to discover its own authorization server (RFC 8414), register a client (RFC 7591, falling back to a fixed public id when the server names no registration endpoint), and run the existing PKCE/loopback browser login, storing the result under a reserved `mcp:<server>` credential-store key; the dial sends the bearer proactively and retries once, refreshed, on a `401` that carries `WWW-Authenticate` (**D466**, `ganja-provider/src/auth/mcp_oauth.rs`). No upstream counterpart for any of the three — opencode dials once and refuses the `oauth` key by name.
- `lsp/` — language servers, opt-in by config and spawned lazily by the first touch of a file they claim. Diagnostics — errors only, pushed and pulled, merged and deduped — are appended to `edit`/`write` results at one seam in `session.rs`; no LSP failure may fail a tool call or a turn.
- `plugin.rs` — Claude Code's `.claude-plugin` plugin and marketplace shapes, verbatim (**D472**, `claude-plugin-spec`; upstream opencode has no plugin system at all), over an install store at `<config home>/plugins/` whose only doors are the explicitly typed `ganja plugin` subcommands and the `/plugin` dialog — install is the consent, because a plugin's hooks and MCP servers run with the user's own authority. Foreign files are read tolerantly (Claude ignores unknown manifest keys, so this parser does too) but every name is refused at parse if it could escape the store, and a marketplace add stages, validates, then moves — no failure leaves half an add behind. At config load each enabled plugin becomes a **config contributor**, merged per surface at exactly one point in `Config::load_with` rather than as a fourth tier through `Config::merge` (**D473**, `plugin-component-merge`): hooks *append* beside config-declared groups, MCP servers arrive namespaced `plugin:<name>:<server>` and ask by default, `skills/` concatenates onto the roots, `commands/*.md` join the `command` table namespaced `<plugin>:<name>` — Claude's own spelling for a plugin command — read by the very loader a project's own `.ganja/commands` goes through rather than a second parser, and agents and LSP entries merge per key with the explicit config winning and the collision reported by name. Six surfaces, and the sixth (commands) closed the set in P22. One collector walks a plugin's components for the listing and the load path both, which is what keeps `ganja plugin list`, the `/plugin` dialog and what a session actually serves one answer.
- `agent.rs` / `instruction.rs` / `command.rs` — who a turn runs as (build, plan, general, explore, plus whatever the config adds), the system prompt it runs under (a base prompt per model family, the `<env>` block, the `AGENTS.md` family — including, since P15, the nested files a touched subtree earns lazily (**D480**) and the opt-in memory section (**D478**)), and the slash commands it can run. A command's template expands the way upstream's does: `` !`cmd` `` runs through the passthrough's spawn at the project root and substitutes its output, and `@file` attaches the way a composer mention would.
- `config.rs` — `ganja.jsonc`/`ganja.json` across three tiers, under the environment and the flags. Unknown top-level keys are refused by name. `hooks`, keyed by event name, is Claude's own `{matcher, hooks: [{type: "command", command, timeout}]}` shape kept verbatim for migration familiarity, refused unknown by event name and by handler `type` alike; `agents.concurrency` (default four, refused at zero) caps how many `task` calls one assistant step runs at once — its own settings object beside `agent`'s per-name map, not a key inside it, since a `concurrency` key living in that `BTreeMap<String, AgentConfig>` would collide with an agent actually named that (**D462**); an MCP entry's `output_limit` (bytes, not the catalog's tokens) and a remote entry's `oauth: {}` marker are the two other P13 additions, all curated and refused by name at load like everything else here. P15's `memory` (bool, absent = off) is the opt-in for the per-project auto-memory section (**D478**); P16's statusline roster gained the `rate` element (**D484**); P17's `effort` (string, absent = none) seeds a *fresh* session's catalog effort through `Engine::seed_effort` — a default, not an override, so a resumed row's own effort wins, and a name the selected model does not serve clears with a log line at adoption rather than refusing the config at load. P20's `openrouter` table (`server_tools`, a list validated against the vendor's documented roster and refused unknown by name) is the opt-in for that gateway's server-run tools, which bill per call (D489). P14 added the curated `tui` table — `notifications` (bool or event filter), `notification_method` (`osc9`/`bel`), and `statusline` with its named-element roster, an unknown element name refused at load by name — the one config surface that exists purely for the terminal frontend, still parsed and refused here because this file is where every key is either curated or refused.
- `storage.rs` / `snapshot.rs` — versioned session storage in one SQLite database per project, converted from the old file tree on first open, and the working-tree snapshots `/undo` walks. Credentials and the model catalog moved to `ganja-provider` and are still named here as `ganja_core::auth` and `ganja_core::catalog`.

**`ganja-tui`** — every pixel, no engine logic. It links `ganja-protocol` for the types it renders, `ganja-permission` for the stored rules it loads and hands to the engine, and `ganja-tool` for the one thing it runs in-process, the `@` menu's glob walk. One `tokio::select!` owns all mutable UI state; `App::handle` is the only mutator, which is what makes components testable without a terminal. Frames coalesce to 16ms for streaming bursts; a keystroke redraws immediately. Themes are loadable data (four ported from upstream, plus whatever `<config home>/themes/` holds), the palette and the `/` menu are two views of the same command set, `@` raises a file menu, and a leading `!` hands the line to a shell. Both inline menus complete on Tab as well as Enter — the file menu inserts the selected path exactly as Enter does, the slash dropdown completes the buffer to the command name **without** running it (Claude Code's own screenshots; upstream's Tab dispatches the row like Enter, D446) — and Ctrl+L forces the next frame through a full redraw, the same `stale` flag the external editor's return path already sets (D445, no upstream counterpart). `/copy` and `/copy-message` put the conversation or the last reply on the clipboard — through arboard and upstream's OSC 52 escape both, so a copy lands even over ssh or tmux — pasted text arrives whole through bracketed paste, a drop or paste of one or more existing (or `file://`) paths becomes `@`-mentions instead of raw text (every token must resolve or the whole paste stays literal), Ctrl+V pastes a clipboard image as a PNG encoded in-process and attached through that same mention pipeline — shown in the composer as Claude Code's own `[Image #N]` token since 2026-08-15, the number mapped back to the saved file at send time while the token stays in the text; a Finder-style **file copy** is read off the pasteboard's file list *before* its decoy basename text — Claude Code reads the same metadata as `«class furl»` — its image files tokenized against the copied file itself, everything else classified as a drop would be (D449; D111 now names only the long-paste-folding half still unbuilt), and a configured MCP server that cannot be reached is named in the status bar. The composer keeps upstream's prompt history (fifty entries on disk, walked with Up/Down from an empty or unedited buffer), breaks lines on `shift+enter`/`ctrl+j`, and its `@` mentions name line ranges (`@file#5-9`) and attach images and PDFs, with a submit-time warning when the selected wire cannot carry one. Ctrl+R opens a fuzzy-filtered, newest-first search over that same prompt history with a full preview of the entry under the cursor (Claude Code's own panel; upstream's Ctrl+R is unrelated — `session_rename`, which ganja has never bound, D447). A message typed while a turn is already running does not wait for the next one: it steers, sent as `Command::Steer` and rendered in a queue strip above the composer until the engine drains it into the running turn at its next step boundary (`Event::SteerConsumed`); what cannot steer — a refused or still-unconsumed entry, a slash command, a shell line — falls back to a FIFO replayed once the engine goes idle again (D450). `/rewind`, and a second Esc within 500ms of the first at an idle composer (Esc alone still cancels a streaming turn, D452), open a two-step checkpoint picker over the session's own user messages — Claude Code's presentation on upstream's message-level revert — whose second step chooses `RevertScope::Both`/`Conversation`/`Files` (D451) before sending `Command::RevertTo`. The question dialog takes a typed answer unless the tool said `custom: false`, and `/effort` picks a catalog effort for the active model, shown beside the model name in the status bar. Ctrl+T raises a full-terminal-takeover inspector — three tabs (expanded transcript, raw event log, per-turn token table) switched by Left/Right or 1/2/3, no border or centering — over whatever `themes_open` gave up to it: that action's own default chord is now empty, reachable only through `/themes` or the palette (**D453**; the presentation is a synthesis of the OpenAI Codex CLI's own overlay for the takeover and banner, and Claude Code's Ctrl+O mode for the one-line footer). `/mcp` is a new two-step dialog — one row per configured server (status glyph, tool count, first error line), Enter opens a per-row action menu offering Reconnect for a `Failed` row and Login for any row whose server is configured with `oauth` (**D465**), status kept live by the same poll-on-`Tick` pattern every other status surface here already uses. The status bar gained three appear-only-while-nonzero segments: `N bash running` (background jobs), `N tasks running` (shown only above one — a lone `task` call is already named by the activity segment), and `N dialog(s) queued` (a permission or question wait behind the one dialog on screen) — all three read off polled engine state rather than tracked as tallies of their own (**D462**). Esc Esc at an idle composer now enters a Codex-style backtrack walk rather than the rewind picker (**D467**, amending D452's gesture while keeping its both-presses-idle guard): the newest user message lights up in the transcript, each further Esc steps one older, Enter reverts the conversation to before it **and hands that prompt back to the composer for editing**, and any other key exits without reverting — `/rewind` keeps the Claude-style two-step picker. A curated `tui` config table drives two more surfaces: `tui.notifications` (a bool or an event filter of `turn-complete`/`approval-requested`) writes one OSC 9 — or, as `notification_method: "bel"`, one BEL — to the terminal when a turn ends or a dialog waits **while the terminal is unfocused**, gated off the focus events crossterm already reports (**D468**, the Codex CLI's `[tui] notifications` behavior); `tui.statusline` turns the status bar into an OMC-HUD-shaped roster of named elements — user-ordered, width-aware, meter-shaped context segment included, with optional git and detail lines — whose absent-config default renders exactly the fixed bar this build always drew (**D469**). `/context` renders Claude Code's per-category grid over `Engine::context_breakdown()`'s estimate, degrading to honest totals on an unsized model (**D470**); `/usage` renders session totals, cache and reasoning splits and the inspector's per-turn table over what this side already holds, and real plan-limit meters where a backend serves them — the codex backend's 5h/weekly used-percent windows and Copilot's quota snapshots, off every response's headers (**D485**) — with the honest-absence tail (**D471**, narrowed again) naming only the credentials that serve nothing. `/plugin` is a two-step dialog over the plugin store in `/mcp`'s shape (**D474**): one row per installed plugin (state, origin marketplace, per-surface component summary off the same collector `ganja plugin list` prints), Enable/Disable/Remove per row, and Add marketplace / Install / Reload as row-independent actions — the Add/Install text taken by a TUI-local free-text step that reuses the question dialog's rendering and never rides an engine `question` round trip, a failed clone's captured git stderr surfaced on the dialog's own notice line, and Reload reporting the honest split: hooks and skill roots rebuild in-session through the engine's narrow replace seams, while agents, MCP dials and LSP servers are named "restart required" rather than half-reloaded. The transcript pane itself now draws **Claude Code's own grammar, taken from a screenshot** (**D487**): `>` on a prompt, `●` on every reply block and every tool call with its arguments condensed onto that one line (`● Edit(filePath: "a.rs")` — capped, and admitting the cut), `⎿` on what a call answered with its clamped preview hanging under that marker's own measured columns, and `✻` on thinking. A call's state is told by color rather than by a bracketed word, so its header reads identically running and settled; the clamp hint names ganja's own expander (`… +N lines (ctrl+t to expand)`, where Claude's names ctrl+o). Two tools are deliberately special-cased: a delegated `task` keeps upstream's facts in the new dress — and, while it runs, hangs the child's own recent calls under the row off a capped log the watcher writes into the part's metadata, the full log one `/copy` or transcript expansion away (2026-08-15) — and a `read` shows `● Read(/abs/path · lines A-B)` and `⎿ Read N lines` with **no preview at all** — the file's content is what the model asked for, not something to read back to a person through a four-line window. While a turn runs, a strip **pinned above the composer** — outside the scroll entirely, sized fresh into `App::draw`'s vertical split each frame — carries `✻ <verb>… (Ns · ↓ N tokens)` painted its own orange with a brighter band sweeping left to right, and under it the running turn's newest `todowrite` checklist; a settled call's `●` answers the verdict alone — the theme's success green, or its error red with the failed heading kept prose (three 2026-08-15 screenshots, amending D487's tail seam). Its verbs are ganja's own and its token figure the session's running output total, dropped rather than shown as a zero. `/copy` keeps upstream opencode's markdown shape throughout: the screen and the clipboard are read by different readers, and only the screen moved.

**`ganja-serve`** — the engine over a socket: the legacy `/session/…` REST surface and a `GET /event` SSE stream, driving the same `Engine` the TUI does and inventing no state of its own — `GET /permission` is the one derived view, kept by a lossless subscriber that only moves map entries. Three postures are pinned by its tests: a non-loopback bind with no password is refused at startup (a deliberate divergence from upstream's warn-and-serve), the launch directory is the only directory served (anything else is `400`, never a silent answer about the wrong worktree), and no query string ever reaches a log line, because `?auth_token=` is a credential in a URL. The SSE stream opens with a `connected` frame, heartbeats every ten seconds, and ends an evicted subscriber with an observable `evicted` frame rather than a silent close; `EngineError` maps `SessionNotFound`→404 and `Busy`→409, with unparseable payloads at 400.

**`ganja-client`** — the other end of `ganja-serve`'s wire, and nothing else: the typed routes and the SSE reader that `run --attach` drives. Its internal dependency list is exactly `ganja-protocol` (CI-gated) — a client that linked the engine would be a second frontend rather than a consumer of the first one's socket. The server's frame vocabulary (`connected`, `heartbeat`, `evicted`, and the event payload) is declared on this side and pinned against a real server; a frame or field outside the declaration is refused readably as version skew, never guessed at, and the credential comes from `GANJA_SERVER_PASSWORD`/`GANJA_SERVER_USERNAME` through serve's own resolver so the two ends cannot disagree about which variable means what.

**`ganja-cli`** — clap; no subcommand starts the TUI, one of them — `run` — takes a whole turn without it, driving the same engine headless and writing either readable lines or one JSON object per event (or, under `--attach`, the same account of a turn taken on a running `ganja serve`), and another — `serve` — puts the same engine behind HTTP and SSE until a signal ends it.

### Testing Requirements

The four gates above, all green, before a phase is called done. Unit tests live beside the code in `#[cfg(test)] mod tests`; anything needing a real socket, a real filesystem layout, or process-wide environment mutation goes in a crate's `tests/`.

### Common Patterns

- Test names are sentences about behavior: `a_denied_edit_leaves_the_file_untouched`, `a_second_subscriber_sees_the_same_events_the_first_does`.
- A test that mutates process-wide state gets its **own test binary**. nextest already gives each test its own process, but the separation still holds the line under a plain `cargo test` (which runs a binary's tests on parallel threads) and keeps the intent legible.
- Anything touching stored state redirects `XDG_DATA_HOME` so it cannot read or write the real user's credentials, permissions or spilled output.
- Nothing may render a whole API key; `crates/ganja-core/tests/secrets_env.rs` pins that with a canary.
- Commit subjects are `scope: intent` — the crates touched, then why (`core,tui,cli: let the model act through permission-gated tools`).

## Beads Workflow Integration

This project uses [beads_rust](https://github.com/Dicklesworthstone/beads_rust) (`br`/`bd`) for issue tracking. Issues are stored in `.beads/` and tracked in git.

### Essential Commands

```bash
# View ready issues (open, unblocked, not deferred)
br ready              # or: bd ready

# List and search
br list --status=open # All open issues
br show <id>          # Full issue details with dependencies
br search "keyword"   # Full-text search

# Create and update
br create --title="..." --description="..." --type=task --priority=2
br update <id> --status=in_progress
br close <id> --reason="Completed"
br close <id1> <id2>  # Close multiple issues at once

# Sync with git
br sync --flush-only  # Export DB to JSONL
br sync --status      # Check sync status
```

### Workflow Pattern

1. **Start**: Run `br ready` to find actionable work
2. **Claim**: Use `br update <id> --status=in_progress`
3. **Work**: Implement the task
4. **Complete**: Use `br close <id>`
5. **Sync**: Always run `br sync --flush-only` at session end

### Key Concepts

- **Dependencies**: Issues can block other issues. `br ready` shows only open, unblocked work.
- **Priority**: P0=critical, P1=high, P2=medium, P3=low, P4=backlog (use numbers 0-4, not words)
- **Types**: task, bug, feature, epic, chore, docs, question
- **Blocking**: `br dep add <issue> <depends-on>` to add dependencies

### Best Practices

- Check `br ready` at session start to find available work
- Update status as you work (in_progress → closed)
- Create new issues with `br create` when you discover tasks
- Use descriptive titles and set appropriate priority/type
- Always sync before ending session
