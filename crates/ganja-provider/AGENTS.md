# ganja-provider

## Purpose

Talking to a model vendor: the wires, the credentials they present, and the table that sizes and prices what they serve. A wire turns a `ChatRequest` into HTTP and an HTTP response back into a stream of `ProviderEvent`s. It knows nothing about sessions, tools, snapshots or storage — and with `ganja-core` outside this crate's dependency graph, that is the compiler's rule rather than a convention a reviewer has to keep holding.

**One crate, not three.** Auth and the catalog fold in here rather than standing on their own, and the reason is the direction of the traffic between them. The auth→provider edge is a single function (`provider::reachable_in_the_clear`, consumed by both browser logins' endpoint checks — `auth/openai.rs`'s redirect check and `auth/mcp_oauth.rs`'s two); the provider→auth edge is some forty-odd references reaching per-provider submodule internals — every wire resolves its credential through `auth::Refresher`, and three of them implement `auth::RefreshOauth` against their vendor's token endpoint. The catalog is tangled with auth in the other direction again: it reads a fetched payload's keys through `auth::provider_id_for_storage_key`, because a row filed under upstream's name for a vendor is a turn nothing can price. A boundary drawn between any two of these would carry no invariant anyone would gate, and a boundary nobody would defend is worse than none — it invites the traffic and then fails to describe it.

**What did not move: selection.** `ganja_core::provider::select` reads a `Config`, so it stayed where the config is, over a glob re-export of this crate's `provider` module. Everything here takes plain data instead — an id, a dialect, a base URL, a credential, a header map — which is exactly what made the split possible. `CompatProvider::new`'s doc comment has said so since before there were two crates.

## Architecture

**Decisions the cursor wire owns.** Every other wire in this directory ports an upstream file; cursor's has none, so its rulings are stated here rather than cross-referenced to a port. The three below — **D550**, **D552**'s wire half and **D553** — are stated in full and summarized in the root `AGENTS.md`; the engine-side halves of the first two (`ToolReach`, the builtin door, the bridge's execution-site test) are `crates/ganja-core/AGENTS.md`'s, and D553 has none.

**D550** (2026-09-05, `.omc/plans/2026-09-04-cursor-tool-bridge.md`, W1), **amending D486**: a server exec this build will not serve is refused **in the kind's own vocabulary**, not on the control channel's throw. D486 answered every exec with `throw` + `stream_close` (`index.js@4272747`) because that was the one branch of the shipped dispatcher that had been read — and it is the client's **no-handler** path, what it writes when nothing claims a server message at all. A *decline* is answered elsewhere in that client and differently: the handler returns the kind's typed `rejected` arm with the reason in it (`index.js@5487600` for a delete, `@5329600` for a shell; twelve such sites across the handlers). The difference is what the model on the other end reads — a rejection is a tool outcome it adapts to, a throw is a client that broke — so this build was sending the broken-client shape for a decision it had made deliberately. `request::refusal_answer` now answers ten kinds at their own field numbers, echoing back what the args named (the command, the path, the url) and then the `stream_close` that ends every exec, refused or served; `redacted_read_args = 29` is in the table because its result resolves to the same `ReadResult` descriptor kind 7 does, so the arm was free. Two of the ten have no `rejected` arm in the shipped descriptor at all (`grep_result`, `fetch_result`), so their refusal travels as the `error` arm, the only place those results can say anything. **The throw survives as the catch-all**, and that is the half of D486 that was load-bearing: its channel is keyed on the numeric id alone, naming neither kind nor `exec_id`, so an exec of a kind newer than any table here is still refusable and no kind is left to hang a turn. Landed with three execution deviations, each recorded because it widened the ruling: every typed refusal is followed by `stream_close` (the shipped client closes after every handler's last frame, not only the streamed kind), `exec_kind`'s table grew to the bundle's 23 further kinds so a refusal names the kind rather than a field number, and `ExecRefusal` carries `exec_id`.

Beside the refusals, D550 owns **the switchboard — asking the server for less**. `RequestContext` (`@6467399`) carries booleans that decide which execs the server's loop generates at all, and this build sets **only** what demonstrably produces an exec it cannot serve: `mcp_file_system_options = 23 {enabled: false}` (the MCP filesystem meta-tool asks for descriptors and filesystem execs ganja serves none of), `read_lints_enabled = 35 → false` (it drives `diagnostics_args = 9`, a kind with no modelled arm and no ganja equivalent — ganja's LSP diagnostics ride `edit`/`write` results), and `web_fetch_enabled = 24`, which is **not a literal**: it is `serves_fetch`, the **wire-local** predicate `!request.tools.is_empty()`. Wire-local is the ruling, not an accident — `ganja-provider` declares no `ganja-core` dependency and `depgate.toml` forbids it one, so the switchboard cannot name `ToolReach` where the switchboard has to be written, and a request's own roster is the honest local signal: this client can serve a `fetch_args` exactly when the engine offered it tools to redirect one to. `web_search_enabled = 17` is **left unset deliberately** — server-side search may need no client exec at all, and disabling it on suspicion would cost the seat a capability for nothing — and `search_conversations_enabled = 50`, `send_message_enabled = 51` and `mcp_meta_tool_options = 34` are left unset because absent is already off; they are named in the code so a reader knows they were considered rather than missed. Since **D552** the predicate is *nearly* rather than exactly what its doc says: a roster without `webfetch` still answers `true` and then refuses the exec, a known residue with a bead against it rather than a silent edit, because AC-3's tests pin the predicate and narrowing it to `roster.contains("webfetch")` is a behaviour change of its own.

**D552** (2026-09-06, same plan, W4; the engine half is `ganja-core`'s) — **ganja's own tools run on this wire**, through a Run the wire holds open. Its specification is a recorded live probe (`tests/fixtures/cursor-mcp-tools-probe.txt`, five user-run turns): the server offers and calls a client-declared tool under a synthetic `provider_identifier`, a 25-second hold on the run-level heartbeat alone survives, typed refusals keep a turn alive, `system_prompt_spec.append` is ignored outright, and the schema field question answers **both**. Where the plan's prose and that recording disagreed, the recording won.

- **The declaration.** `request::declaration` turns `ChatRequest.tools` into `McpToolDefinition{name = 1, description = 2, provider_identifier = 4, tool_name = 5}` on the run request's `mcp_tools = 4` and on every `RequestContext.tools = 7` answer — both channels, which is where the shipped client puts them. `name` and `tool_name` are both the registry name, as the shipped builder sets them (`index.js@5699717`). The schema rides `input_schema_json = 6` **alone** even though the probe measured field 3 working too: it is already a JSON string on this side, and two encodings of one schema are two things that can disagree. An empty roster declares nothing, and an empty repeated field encodes to no bytes, so a title or summary one-shot sends byte-for-byte what this wire sent before the bridge existed. **The naming ruling:** `provider_identifier` says who *serves* a tool and `"ganja"` is true — this is not a claim to be an MCP server, it is the channel cursor calls MCP being used by the client that runs the tools. One `pub(super)` constant serves the declaration and the inbound match, so the two cannot disagree.
- **The inbound arguments** are the one genuinely new decode surface: `McpArgs.args = 2` is `map<string, google.protobuf.Value>`, so `cursor/value.rs` models that well-known type's oneof and converts to `serde_json::Value`. It **restores the integer spelling of an integral double**, which is a defect a test caught rather than a nicety: `Value` has only a `double` arm, so a model writing `40` arrives as `40.0` and `serde_json` refuses to deserialize a `u64` from a float — `read`'s own `limit` would have been rejected as "invalid type: floating point" for a window the model spelled correctly. JSON draws no such distinction, so the round trip is lossless in the direction that matters. A shape the decoder cannot read fails **that one call** with `McpResult.error`, never the turn.
- **The inbound order**, in `cursor.rs::mcp`, and each arm is a ruling: `smart_mode_approval_only = 7` set → answer `approved = 7` and close, **executing nothing and emitting no tool-call events**, because a policy question that ran the tool would run a side-effecting `bash` or `write`, possibly twice; a **present** `provider_identifier` that is not `"ganja"` → `server_not_found{name, available_servers: ["ganja"]}`, never run — an **absent** one is not somebody else's name and refuses nothing, and a present `server_identifier = 9` refuses nothing either, because the recording has it present on every normal call; an unreadable argument map → `McpResult.error` for that call alone; a name outside the roster → `tool_not_found{name, available_tools}` filled from what this request declared — except on an **empty** roster, where the answer stays D550's `rejected`, since claiming a name is missing from a roster implies a roster exists; otherwise bridged. A call this wire cannot hold — nothing to pause under — is refused for the hold rather than the roster, in its own sentence.
- **The native redirect table** (`cursor/native.rs`), because declaring MCP tools does not stop the server asking for native kinds: seven exec arms onto six of ganja's own tools — `read_args` and `redacted_read_args` → `read` (the redacted answer riding field 29), `shell_stream_args` → `bash`, `grep_args` → `grep`, `ls_args` → `glob`, `write_args` → `write`, `fetch_args` → `webfetch` — each with its argument mapping stated and pinned by a test that decodes the frame back off its own bytes, so a field number is what is asserted. Four mappings are rulings rather than transcription: case-insensitivity is folded into the pattern as `(?i)` because ganja's `grep` has no flag for it and decoding the member and ignoring it would answer a different search; a **negative** `ReadArgs.offset` is dropped rather than passed on, since `read`'s offset is an unsigned line number and `-3` reaches its deserializer as a broken tool where the model asked for a window that does not exist; an `ls_args` is redirected only when its path is **absolute** (`glob` answers with absolute paths and the tree is built by stripping the directory off each, so a relative path names no directory the two ends can agree on) and a listing whose entries lie elsewhere answers on `error` rather than as an empty directory, which would be a fact this build did not measure; and the **`FileTimes` ruling** — a `write_args` for a file this session never read is refused by ganja's own `write`, and that refusal rides `WriteResult.rejected{path, reason}` naming the read-first requirement, which the model can act on by asking for a `read_args` first. **A redirect happens only when the mapped tool is on this request's roster**: a turn not offering `bash` does not run a shell because the server asked, and that exec keeps D550's typed refusal — which is what makes "refused" still mean something, a statement about what this turn is offering rather than about what this client can do.
- **The pause** (`cursor/bridge.rs`) is the mechanism the W3 gate chose from four, live measurement in hand (**Option 1, paused duplex**; the user's choice, recorded in the plan). Cursor's Run is a duplex whose request body stays open and whose server generates by *asking*; ganja's engine runs tools **between** provider calls. The two shapes do not meet, so the stream **pauses** rather than ending: a bridgeable exec is surfaced as an ordinary tool call, the step finishes, and the whole fold — response body, splitter, mapping, request-body sender, blob store — moves into `HeldRuns` under the key the *next* request will also compute. That key is **`(model, messages[turn_start].id)`**, the reference's own shape (`proxy.ts:1319`), because it must be computable from a `ChatRequest` alone and stable across the turn's resumes. Matching the pending execs' call ids against the resumed request's tool results is a **confirmation** of that hit, never the lookup. A keeper task sends the run-level `client_heartbeat = 7` every `HEARTBEAT` (5 s) whenever a body is open; **no exec-level heartbeat is sent at all**, because the probe measured it unnecessary, and `ExecControl.heartbeat = 3` left the proto with the spike.
- **What must never be dropped**, since one engine drives a title one-shot, a compaction summary and up to `agents.concurrency` subagent turns through the same `Arc<dyn Provider>` while a root turn is held: a `stream()` **never drops a held run it does not key to**. A keyed miss opens a fresh Run; a keyed hit whose confirmation fails opens a fresh Run and leaves the held run *intact*; only a differently-keyed request carrying another held run's results evicts that run, since nothing can ever resume it. The three drops are the pausing turn's cancellation, that eviction, and `IDLE_BOUND` — **600 s**, chosen as the strand backstop rather than a guess at a server timeout (the probe proves 25 s and says nothing above it): a permission dialog a person is answering and a two-minute shell command both fit inside it, at the cost of one socket and one task for ten minutes when a turn pauses and never resumes. Each drop is remembered in a 16-entry ring with its reason, which is what the recovery's log line names. At this landing a resume whose held run was gone failed **by name** rather than silently re-opening a fresh Run, because the wire then carried no history at all and such a Run would have forgotten what the tool answered; **D553** below is the landing that made it a recovery instead.
- **Nothing is executed in this crate**, and that is the invariant `depgate` cannot express: `depgate.toml` already permits `ganja-provider → ganja-tool, ganja-permission`, so a redirect that ran the tool here would redden no rule — it would simply have no dialog to raise and no transcript to write, silently downgrading the permission posture to static rules. `native.rs` names no `ToolCtx`, no `Registry` and no `.run(`; a redirect produces a name and a JSON object. The invariant is a **test** in `ganja-core` (AC-17), because only that crate can drive both ends.
- **Telling a refusal from a failure** without seeing the engine is what `ganja_tool::permission_text`'s refusal sentences are for (`REJECTED` and `DENIED_PREFIX`, hoisted in this wave): an `Error` tool part whose text is one of them becomes the kind's `rejected` arm, and every other `Error` becomes `success{is_error: true}` — cursor's own shape for a tool that ran and failed. This wave spelled that test inline in `native.rs`, naming both of them directly, which is exactly what **D556 amended** (its paragraph below states the amendment in full): there are **three** sentences, the third being the one a `PreToolUse` hook block leaves, and `permission_text::is_refusal` is now the single predicate that enumerates them — so this wire no longer reports a hook-refused call as one that ran and broke. `native::READ_FIRST` is a *copy* of `ganja-tool`'s read-first sentence rather than a hoist, proved by a test that builds the refusal through the real `FileTimes`; hoisting it beside the other three is a follow-up.
- **Construction is store-free.** `CursorProvider::at(base_url, CredentialSource)` takes its credential as a value, so the engine-level bridge suite has no code path to `auth.json` at all — structurally stronger than redirecting `XDG_DATA_HOME` away from it, and the reason that suite can be one binary rather than one binary per test (`redirect_xdg_data_home`'s documented invariant is one test per binary). `CredentialSource::key` and `Clone` came with it, chosen over making `Presented::new` public so a caller may **build** a credential source and still not read what is inside it. All three doors — `CursorProvider::at`, `CursorWire::at`, `CursorWire::from_stored` — delegate to one private constructor, so the shipped path *is* the tested path; `check_base_url` still runs, so a caller supplying its own token cannot send it anywhere a key could not go.
- **Modelled only what this wave reads or sends**, per `cursor.proto`'s own rule, each named in its message's comment rather than silently absent: `LsArgs.ignore` (ganja's `glob` has no ignore argument, so a decoded-then-disobeyed list would claim a narrowing this build does not perform), `McpResult.permission_denied` (a denial reaches this wire as ganja's own refusal sentence and rides `rejected` whole), `GrepArgs.output_mode` (the redirect asks `grep` for matching content, the mode the tool has) and `FetchSuccess.status_code`/`content_type` (`webfetch` reports neither, so filling them would be inventing them). `RunRequest.system_prompt_spec = 29` and `SystemPromptSpec` are **gone**: the probe measured the server ignoring them with no error at all, which is bead `ganja-code-r7jk` and a thing not to retry.

**D553** (2026-09-07, `.omc/plans/2026-09-07-cursor-history-blobs.md`, W1 `4a9ac1d` and W3 `d8fc38e`; **amending D552**'s "fails by name" clause) — **a fresh Run carries the conversation.** Until this landing the run request named its history nowhere: the newest user turn rode `user_message_action` and everything before it stayed on this side, which is why D552 had to make a resume whose held Run was gone a *named failure* — a fresh Run would have forgotten what the tool answered. Now `ChatRequest.messages` before the newest user run is composed onto cursor's **blob channel** (`cursor/history.rs`): `ConversationState.root_prompt_messages_json = 1` holds one JSON entry per system prompt and per history message, `turns = 8` one `ConversationTurn` per user message with its steps as `ConversationStep.assistant_message` blobs, every blob content-addressed by its raw 32-byte sha256 and served from the Run's own store to the server's kv gets (`request::kv_answer`, `:591`; the store is seeded before the stream opens, `cursor.rs:456`/`:531`) — the reference's own composition (`proxy.ts:720-803` at `a37a6ba`, MIT, behaviour only, attributed in the module doc at `history.rs:3-11`) with five deliberate divergences stated beside it (`:37-57`). Its specification is a recorded live probe again, `tests/fixtures/cursor-history-probe.txt`: two user-run turns (probe 1) whose second reply recalled a code word only the first prompt held, the server fetching all six root entries and the turn wrapper and **never** the inner user/step blobs, every get found, no error frame of any kind — the reference's claim that the server builds its prompt from the root, observed from the client side — and a second recording (probe 2, the recovery itself, `ganja.2026-09-07.log:7039-:7085`, written to the fixture's `== probe 2 ==` section as this lands). Where the plan's pre-probe prose and a recording disagreed, the recording won.

- **The walk and the boundary.** `request::newest_user_run` (`:691`) is the one bound the action and the history both read: the newest user *run* — every user message back to the reply before it, never past `turn_start` — is the action, and `messages[..first]` is history, so the two cannot disagree about which message is the last of the conversation and which the first of the turn. `history::entries` obeys the anthropic encoder's `PartBody` exclusions plus `File`, in the one exhaustive match (`pieces`; no `_ =>` in the file): a user message becomes a `user` text entry; an assistant reply becomes an `assistant` entry carrying its text and, as text, each tool call it made, then one `[Tool Result]`/`[Tool Result (error)]` `user` entry per call in call order — a `Pending`/`Running` call renders `NO_RESULT` as an error result, the rule every other wire applies to a call whose turn died — and a message contributing nothing contributes no entry; a compaction summary is carried in the root and dropped from the turns. The system head is inserted **only beside history** — omitted for an empty prompt and for a history contributing no entry (Dv-4) — so a request with nothing before its newest run sends the empty state it always sent — the one new thing on such a request is `conversation_id`, and AC-4 (`tests/cursor_wire.rs`) pins a title one-shot over the socket with empty root and turns, the id present and no `mcp_tools`.
- **The `[Tool Call]` text the reference does not write** (plan Deviation 5). The reference keeps assistant text and tool *results* and loses the call (`proxy.ts:657-661`, `:793-800`); this build renders `[Tool Call] <tool> <compact JSON>` paragraphs beside the text, because on a recovered turn a model shown a result it never asked for is the model most likely to re-issue the call and run its side effect twice. Each input is cut at `CALL_INPUT_LIMIT` (8 KiB, `history.rs:83`) on a char boundary with `… [+N bytes]` naming the exact omission, so a `write`'s file content does not ride every later request whole; `Composed.clamped_calls` counts the cuts and the composition line logs the count (never a byte of text). Probe 1 measured the shape accepted a wave early: its first run made three calls, so its second request was the first this build ever sent carrying `[Tool Call]` paragraphs and both result flavours, and the reply was correct.
- **The ids.** History user-blob `message_id`s are `history::derived(&MessageId)` (`:614`): the first 16 bytes of `sha256(seed ‖ id)` rendered v4-shaped through the same `render_v4` `fresh_id` uses — the reference's `deterministicUuid` layout (`proxy.ts:1341-1351`) from a seed that **survives compaction**, where the reference's turn-index-and-text seed (`:786`) would re-mint every id on a shift (plan Deviation 7). The **action's** `message_id` stays `fresh_id()`, random, exactly the reference's `crypto.randomUUID()` (`:849`): the plan's first revision proposed deriving it too, and both reviewers showed the equality it bought had no consumer. `RunRequest.conversation_id = 5` **is sent** — `derived` of `messages[0].id`, absent on a messageless request — because the reference sends one on every request (`:877`) and the only composition measured accepted carries it; it is re-rooted by compaction and per-invocation on the one-shots, both harmless because nothing is read back under it and every request carries a complete state (`cursor.proto:139-149`).
- **The resume, and the recovery** (W3; `cursor/bridge.rs:65-98`). A request whose newest message is the assistant's — the shape only a bridged step can leave — goes out under `ConversationAction.resume_action = 2`, fieldless, over that history (`request.rs:241`). That is what a resume against a bridge that is **gone** now does instead of failing: `Closed` and `Dead` are one **`Resolution::Recover(String)`** arm (`bridge.rs:243`) whose sentence names the drop reason out of the ring for the log line (`recovery`, `:458`; `settle`'s closed-body arm keeps its old "closed its request body" wording plus the recovery clause, `:537`), and `stream()` logs `recovering a cursor turn on a fresh run` and falls through to the fresh-Run arm (`cursor.rs:446-448`) — where the finished results already sit in the composition as `[Tool Result]` entries and a call still lacking one as `NO_RESULT`. Probe 2 is this arm live: a `bash` dialog left open past `IDLE_BOUND` dropped the held Run with `Reason::Idle` at exactly 600.0 s (`:7058`→`:7059`), the answered dialog's request recovered on a fresh Run under `resume_action` over a composition of `entries=4 turns=1 blobs=8 bytes=173176` (`:7060`–`:7061`), seven gets found, a clean finish — and **the tool ran exactly once** (the probe file holds one line). The engine sees none of it: a step that continues.
- **The cap: once per key.** Every key recovered is pushed onto `reopened`, a `VecDeque<Key>` bounded at `REOPENED = 64` (`bridge.rs:142`, `:264`) that `drop_run` (`:378`) **never touches** — deliberately, because the shipped shape is recover → the reopened Run held again under the *same* key → dropped again, and a count kept in the drop ring would be shadowed by that second drop's fresh entry (the defect two review rounds converged on). `reopen` (`:439-453`) answers `Recover` on first sight and `Failed` naming the cap after (`capped`, `:468`: "…already reopened once for this turn and is not reopened again"), and it sits at exactly the two sites a `Recover` is produced — the tail arm (`:339`) and `settle`'s closed-body arm at its one call site (`:322`, which first files the drop on the ring as `Closed` through `remember`, `:393`, the ring's one writer — the entry left the table for a resume rather than through `drop_run`, and a capped second attempt reads the ring for its clause, so without that entry it would name the drop *before* this one) — **never before `Resume` or `Fresh`**, so a recovered Run held again and resumed with its results resolves `Resume` as any held Run does: a capped turn loses its second *reopening*, not its ability to continue. The list is scoped to the provider and reset by nothing, which is safe because a `Key` is the opening message's id and ids ascend. Why one: the shipped shapes produce one drop per turn, a second is a condition a person should see, and the shipped client stops its own automatic resumes after two attempts without progress. Proved end to end by AC-16b (`crates/ganja-core/tests/cursor_bridge.rs:1373`): two hangups of one turn, two Runs, then `Failed` naming the cap, each tool run exactly once.
- **Deliberately not sent or read, each with its measurement.** `pre_fetched_blobs = 17`: the shipped client never fills it (bundle grep — two constructor sites, no writer) — a P4 experiment bead cites probe 1's numbers. `conversation_history = 7`: zero senders in the bundle, and a mute-failure asymmetry — a blob get the server cannot answer fails loudly, an inline history it ignores fails silently — so it stays a second *encoder* over the same `History` (the `entries`/`blobs` cut, `history.rs:28-35`) rather than a second walk, to be measured only on the ADR's expiry signals (a material TTFT cost at ordinary lengths, or a recording of the flattened text being misread). The checkpoint arm (`ServerMessage` field 3): reported by `decode::unmodelled` (`:417`) as number and size only — it arrived on every run of both probes, 558 to 7465 bytes — and its `token_details` half is the follow-up bead. `ConversationStateStructure`'s other 34 fields (`cursor.proto:162-165`) are unmodelled because nothing here fills them: they are what a checkpoint carries back, and this build reads no checkpoint.
- **The one question the gate turned on, answered by probe 1.** Whether the server would read client-minted blobs at all: it did — seven gets, every one found, no `Blob not found`, no `invalid_argument`, zero `a server set replaced bytes this run already held` lines. That sizes-only line is `kv_answer`'s overwrite arm (`request.rs:636`), the reference's own `blobStore.set` shape, ruled back from the lane's `or_insert` (Dv-6) because a server re-setting a mutable key and reading it back would otherwise have been served stale bytes; whether that ever happens is what the line measures, and on both probes it never did. Nothing is held across turns: history is rebuilt on every request, the reference's own ground, so whatever the server caches by id stays warm and a re-rooted history costs nothing to re-send.
- **The recorded limitation, stated here because this landing creates it.** The request now **grows with the transcript**, and nothing bounds it: cursor rides the uncataloged tier, emits no `Usage`, and never auto-compacts. The composition's byte count is on every request's log line (probe 1: 171,566 on a one-turn history, 169,304 of it the system head), and reading `token_details` off the checkpoint arm is the bead filed with this landing. `/compact` is the only door in principle, and **it does not open today**, which the `claude-code` landing found rather than this one: `session.rs`'s `compact_if_needed` returns without asking any provider when the model has no catalog row — a manual `/compact` reaches it through the same gate — and an uncataloged wire has no row by definition, so the door is shut here and on `claude-code` alike until somebody designs a manual compaction that does not need a context window to size itself — bead `ganja-code-q3ep` (manual `/compact` reaches no provider on an uncataloged wire), filed at the `claude-code` landing that found it. The fetch's cost is bounded, not measured: on probe 1 the run that fetched 171 KB reached its first thinking 3.7 s *sooner* than the run that fetched nothing — one sample per arm, one afternoon, not a saving.

**What the bridge does not do, stated so nothing here overclaims.** `smart_mode_approval_only` is answered `approved` without ever having been exercised live; the field was absent on all five recorded runs (`ganja-code-nlhw`). The `ls` redirect lists **what a file glob can see**: `glob` matches files and never directories, so the answer is the files directly in the directory — dotfiles included, which a real-directory test measured rather than assumed — plus the child directories that hold at least one file of their own. What it cannot show is an empty child directory, or anything deeper than one level, which is why the tree it fills reports `children_were_processed = false` rather than claiming a walk it did not do. `serves_fetch` still answers `true` for a roster without `webfetch` (`ganja-code-tcfb`), `native::READ_FIRST` is still a copy rather than a hoist (`ganja-code-h7sv`), the retry ladder still runs per bridged step (`ganja-code-hfgv`), and **cursor is still not a row in D521's identity table** (`ganja-code-v2yw`) — neither landing changed what the wire tells the host it is, only what it says. And what D553 does not do: bound the request it now grows (above); carry a `File` attachment into cursor history, which is dropped without a placeholder; or reopen a turn twice.

Ganja's tools run in ganja's cwd, and a CLI under `--tools ""` has no use for one. The consequence is stated rather than hidden: the CLI derives its record slug from that cwd, so every record this wire mints lands under a scratch-derived slug in the CLI's own projects directory, named after a directory the wire deletes at close, bounded by that CLI's 30-day retention and named in the first-spawn log line — a directory a person finds there is this wire's, not a leak.
- **Ganja is the MCP server, and it hand-rolls four methods.** The first stdin line is `initialize` carrying `ChatRequest.system` as `systemPrompt` and `sdkMcpServers: ["ganja"]`; the CLI then dials back over `mcp_message` and ganja answers `initialize`, `tools/list` (the request's own roster, names **bare**), `ping` and `tools/call`. Four JSON-RPC shapes written by hand in `claude_code/rpc.rs` — **no `rmcp`**, which is `ganja-core`'s dependency and not this crate's; adding the edge to serve four shapes would have pinned a provider crate to an SDK's release train for nothing.

Nothing is executed in this crate. `updatedPermissions` is never sent — the shape that would write the user's own settings files — and an `allow` without it records no CLI-side grant, so the next ask for the same tool asks again.
- **What the wire owes the CLI is one rule.** `sent` is the ids of the user messages the wire has written, appended as each is written; every user message in the request whose id is not in `sent` — a turn's prompt, a mid-turn steer, a `/team` continuation block — is written before the turn continues, as one `user` frame when the CLI is between turns. A message arriving **mid-turn is deferred, not carried**: the CLI enqueues each `user` frame as a new prompt, and the one time a carry was measured the model read the second block as injection in the reply the person reads. So a mid-turn steer reaches the model one turn late here; only the deny path carries text mid-turn, because a refusal is text the model reads as the tool's and not as a user's voice. **One class of message may never be remembered** (Dv-22): `Message.request_only`, the guards block the engine mints fresh per *request*, whose new id in the same position would otherwise read as a rewind — which is what it did, respawning the CLI on every `/team` continuation past the first, five paid records per lead turn, until the flag landed.
- **Continuity is the held process, and nothing is ever resumed.** The CLI's own record resumed by the id ganja minted was served on 2 of 8 turns in the recording and refused on 6, so `--resume` is never passed. A live process runs under its **opening** prompt and roster: a change in `system` or `tools` is logged `stale_<what>` once and picked up by the next fresh record, so D480's walk-ins cost nothing while the process lives — while a change in `model` or `effort`, the two values a person chooses, closes the entry and opens a fresh record, honoured at that record's stated cost. Every divergence that needs a new process opens **one** fresh record, logged with its reason word.
- **A fresh record loses the model's own earlier words, and that is measured.** Three runs carrying a rendered transcript *with* `[Assistant]` lines were refused 3/3 by the vendor's safeguard, whose explanation names "duplicating model outputs"; the same transcript without them was served. So the preamble renders `[User]`, `[Tool Call]` and `[Tool Result]` lines and no assistant text, a compaction summary — being assistant text — is rendered as nothing at all, and an ask the model answered in prose alone reads as unanswered. A record opened under `refused-record` renders **no preamble at all**, the shape three runs opened with and were served; `refused_streak` reaching two refuses the next request locally, naming `/compact` and a new session, without spawning — so one ganja process spends at most two consecutive refusals on the account for a key.
- **The bounds, and what each costs in kind.** The process is held across tool turns and user turns, keyed by `derived(messages[0].id)`, under an idle bound (**`claude_code.idle_bound`**, a curated config key — seconds, default 600, refused at zero — suspended while an ask is parked, with a longer stranded bound on a parked ask nobody answers), a silence watchdog of 120 s (sixty times the slowest first frame the recording measured) and an LRU cap over idle entries. **Eight held entries are eight authenticated node runtimes, not eight pids** — which is why the idle bound is the user's key rather than a constant: under this posture the trade is their machine against their conversation. An eviction is surfaced, not merely logged. A one-shot — a title, a compaction summary — never enters the table: one process, one turn, stdin closed, no binding, no MCP server declared. A keyed request whose entry is gone mid-tools is **recovered** once per turn on a fresh record and failed by name the second time, over a bounded ring beside the table rather than a field of the entry the recovery replaces.
- **Ending a process, and being ended.** It ends by stdin EOF, with SIGTERM and SIGKILL as bounds on a process that ignored it; `kill_on_drop` is off because a dropped pipe *is* EOF. `interrupt` is a control request that ends a turn and not a process, and a cancel landing on a parked ask answers it `deny` first. `Provider::shutdown` is a trait default (Dv-14) so a caller reaches it through the `Arc<dyn Provider>` it already holds; this wire's override is the only one in the workspace, and without it a `ganja` that quits leaves up to eight authenticated runtimes alive until their idle bound.
- **The frames it knows, and the ones it refuses to guess at.** A refusal arrives as a known frame — `system/model_refusal_no_fallback` with its category and explanation — and surfaces as a failed turn naming the category with the explanation verbatim; the `result` that follows carries `is_error: true` under `subtype: "success"`, and the wire reads **`is_error`, never `subtype`**, because the CLI's own exit code is the last result's `is_error`. `auth_status`, or an exit before `system/init`, is `ProviderError::Auth` naming `claude login` — kept by construction and marked unmeasured live, the recording's `auth_status` being `{isAuthenticating, output: []}` on every run including a fully logged-in one. Every `control_response` the wire sends is echoed back verbatim and dropped by request id. An unknown inbound frame is skipped, an unknown ask is refused by name and never left unanswered (permission prompts do not time out), and no frame struct uses `deny_unknown_fields` — the opposite of `ganja-client`'s skew posture, and deliberately so: that client's server is ganja's own, this wire's peer is not, and it moves every release. The floor is a version, read once: `from_env` runs `<bin> --version` under a bound and refuses below **2.1.263** naming both versions.
- **What it does not have, said where a reader will look.** The wire is **uncataloged** — no sizing, no pricing, no auto-compaction — and `carries("claude-code")` stays false; `ToolReach` is `Full`. `/effort` nonetheless **works**, on the CLI's own five levels rather than a catalog's, through `effort::standalone`, which is the one definition of the names the engine accepts on this wire; choosing one opens a fresh record carrying `--effort <name>`. `Usage` comes off `result`, and the 5-hour and weekly utilization the CLI reports are `PlanWindow`s, D485's measurement field for field, while `rate_windows` stays the trait default. Readable thinking is empty here until somebody lands the flag that makes a thinking block's text arrive: the default withholds it under a full signature, and this build passes neither flag.

## For AI Agents

### Working In This Directory

- **Nothing here may name `ganja-core`.** CI asserts the internal dependency set is exactly `ganja-permission ganja-protocol ganja-tool` — an allowlist, not a `! grep ganja-core`, so a new internal crate cannot slip in unnoticed. `ganja-permission` is transitive, through `ganja-tool`; the only thing this crate wants of the tools is `ToolDefinition`, which is what a request offers the model.
- **No terminal, no clipboard.** CI asserts `ratatui`, `crossterm` and `arboard` are absent. A login that wants to ask a person something hands the question back to whoever called it — which is why `auth/device.rs` and `auth/loopback.rs` return what they got and store nothing.
- **A credential is resolved per request, never captured at construction.** `CredentialSource` is the seam: a key resolves to itself, an OAuth credential goes through `auth::Refresher::usable`. That is the position upstream's `fetch` override occupies, and it is why a renewal cannot live in the engine — nothing there knows when a token died.
- **Two failure channels, never a completed turn.** A request that never starts streaming fails the call; a body that dies mid-stream ends with `ProviderEvent::Failed`. Retry applies only before the first byte.
- **Secrets never reach a log.** `Presented` is the only type that holds key material and the only place `expose_secret` is called; every `Debug` renders a placeholder, and `Presented::redact` scrubs a credential out of anything a provider echoes back. `crates/ganja-core/tests/secrets_env.rs` pins that with a canary.

### Testing Requirements

```sh
cargo nextest run -p ganja-provider           # unit tests, each in its own process
cargo test -p ganja-provider --doc            # doctests, which nextest does not run
```

Unit tests live in `#[cfg(test)] mod tests` at the bottom of the module they cover. This crate has no `tests/*.rs` binaries: the suites that need a real socket, a real credential store or process-wide environment mutation live in `ganja-core/tests/` and drive these wires through the engine's facade, which is also where the behavior they assert is observable.

### Common Patterns

- Errors are `thiserror` enums whose messages say what the caller can do about it. `ProviderError::is_retryable` is the one classification that is load-bearing rather than cosmetic: it decides what `retry::send` does, and a misclassified refresh failure becomes either a retry storm against an identity provider or a browser login nobody needed.
- Every module doc cites the upstream file it ports, and every deliberate divergence is documented where it happens.
