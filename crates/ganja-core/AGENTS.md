# ganja-core

## Purpose

The engine: session orchestration, the agent loop, and the state a conversation leaves behind. This crate carries **no terminal-backend dependency** — no `ratatui`, no `crossterm` — so the engine stays testable without a terminal and can later be driven over a network transport.

Four things it is built on are crates of their own — `ganja-protocol`, `ganja-permission`, `ganja-tool`, `ganja-provider` — and this crate re-exports each under the module name it always had, so `ganja_core::protocol`, `ganja_core::permission`, `ganja_core::project`, `ganja_core::tool`, `ganja_core::watch`, `ganja_core::auth` and `ganja_core::catalog` all keep resolving. The crate root names the engine's own types and nothing else; a caller that only wants one of the four should depend on it directly — the facade's module names are for the callers that want the engine.

`ganja_core::provider` is the one facade that is not a bare re-export. The wires left; the half that reads a `Config` — which provider a session runs as, which model it asks for — stayed, over a glob of the crate that took them. `src/AGENTS.md` says which functions are on which side.

The bind predicate is therefore **unchanged**, no synthetic peer view or its handler exists, no recipient constant, no second receive ladder, no in-memory inbox and no second drain, and the one-way clauses on a teamless send stay shipped **and stay true**, because the arm that would have made them false still binds nothing. What D533 delivered is three sentences and the decision behind them: `send_message`'s teamless description stopped claiming this build offers no listing tool and points at `list_sessions` instead; `ganja-cli`'s binder comment stopped claiming a lead-only decision the code never made, and now says plainly that the door is handed in unconditionally and that the gate behind it is `ganja-tui`'s own; and the finding itself is on the record here, together with the ruling not to build for a dead arm. Deleting that arm rather than filling it in is filed as a bead, not acted on, because it would reopen D530. **Four execution-time deviations are part of the record.** (**Dv-1**) The plan's envelope id type `MessageId` collided with the conversation-message id of that name this tree has carried since D493, so it landed as `PeerMessageId` — a separate type on `HeldId`'s own precedent; every field name the plan specified is unchanged. (**Dv-2**) The new event and the new answer field forced mechanical completions in five files outside the owning wave — match arms and one `held: None` literal, behavior unchanged everywhere — on the one-mechanical-line precedent this file already records for the sender-side trio, and the not-yet-wired seam items carried a self-clearing `expect(dead_code)` marker until the wiring consumed them. (**Dv-3**) The sender-side receipt registration structurally lives inside `deliver_over_socket`, whose `Sent` cannot carry a message id out to any caller, so the wiring wave was granted a scoped seam on both postboxes — `with_receipts`, the `with_peer_facts` twin — plus the one register call after the POST. (**Dv-4**) The plan's letter had `sender_mode()` calling the engine's receiver classifier live, which is **unbuildable**: both postbox installers run before the engine is behind an `Arc`, so there is no weak handle to hold. It landed by sharing the permission-mode cell itself and calling the same classifier the engine calls — one function over one piece of state, nothing staleable, which is the property that was actually wanted, pinned by a full-cross-product wire test. Under the same deviation the expiry timer's receipt post is spawned out of the expiring task rather than awaited, because the settlement it reports aborts that task and an awaited post would be cancelled by its own subject, every time; one attempt, no retry and its own deadline are all kept. Two execution findings are recorded rather than smoothed over: the sender's 33-entry chain truncation is **unreachable through the engine's own doors** — a receiver refuses past 28, and since the same security review's §1 an adoption keeps at most 27, so the wire tops out at 28 — and its arithmetic is pinned at the facts level over a planted chain instead; and the matrix's self-sent row has **no production producer** in this build, there being no ancestry walk, so it stays unit-tested in the decider's own suite with the site saying why.

## For AI Agents

### Working In This Directory

- **The purity rule is the crate's reason to exist.** CI asserts `cargo tree -p ganja-core -e normal` never mentions `ratatui`. Anything the UI must render is expressed as a serde type in `ganja-protocol`, never as a widget or a style.
- **The four crates beneath this one may not name it.** Each is asserted as a closed allowlist of its own internal dependencies rather than a `! grep ganja-core`, which would go quiet the day a fifth crate appeared: `ganja-tool` is exactly `ganja-permission`, `ganja-provider` is exactly `ganja-permission ganja-protocol ganja-tool`, and this crate is exactly those four. A tool that appears to need something from the engine needs a value in its `ToolCtx` instead; a wire that appears to need one needs another field on its `ChatRequest`.
- **Everything on the protocol is serde-derived from day one.** That serialization constraint — not a trait — is what preserves the path to serving the engine and to persisted transcripts. A new field or variant should be considered wire-visible even though nothing serves it yet.
- The crate root's flat re-exports in `src/lib.rs` name the engine's own types only; a new core module that frontends use re-exports its types there alongside the rest, while a type that belongs to `ganja-protocol`, `ganja-permission`, `ganja-tool` or `ganja-provider` is reached through those module names, never flattened into the root. A frontend that only renders must be able to build against `ganja-protocol` alone, and a root that flattens protocol types into the engine's vocabulary invites the opposite.

### Testing Requirements

```sh
cargo nextest run -p ganja-core               # unit + integration, each test its own process
cargo nextest run --workspace permission      # tests whose name matches "permission", wherever they live
cargo nextest run -E 'binary(golden)'         # one integration binary
cargo test -p ganja-core --doc                # doctests, which nextest does not run
```

Unit tests live in `#[cfg(test)] mod tests` at the bottom of the module they cover; anything that needs a real socket, a real filesystem layout, or process-wide environment mutation lives in `tests/` instead.

### Common Patterns

- Errors are `thiserror` enums whose messages say what the caller can do about it; the taxonomies are deliberately transport-agnostic (`SelectionError` wraps `ganja-provider`'s `ProviderError` across the crate boundary, which is what `#[error(transparent)]` is for).
- Trait objects only where dyn-safety demands it: `Tool`, the subagent seam and (in `ganja-provider`) `Provider` live behind `Arc<dyn _>`, which is why `async-trait` is a dependency.
- Shared mutable state is `Arc<std::sync::Mutex<_>>` for short critical sections and `tokio::sync::Mutex` only where a lock is held across an `.await`. No lock is ever held across an await in a path the render loop depends on.

## Dependencies

### Internal

`ganja-protocol`, `ganja-permission`, `ganja-tool` and `ganja-provider`, re-exported as modules from `src/lib.rs`. `ganja-tui` and `ganja-cli` depend on this crate, and additionally on the protocol, the permission crate, (for the frontend's `@` file menu) the tool crate and (for `auth login`) the provider crate, where they name those types directly.

### External

`tokio` + `tokio-util` (runtime, `CancellationToken`), `reqwest`/rustls (the MCP client's HTTP transport), `futures` (stream combinators), `serde`/`serde_json`, `schemars` (the two schemas the engine builds rather than derives), `ignore` (the `AGENTS.md` walk, under the same ignore rules the tools search by), `etcetera` (XDG paths), `jiff` (the prompt's UTC date), `rusqlite` (the session store), `rmcp` (MCP client transports), `lsp-types` (the LSP wire types), `jsonc-parser` (config files in upstream's dialect), `tempfile` (atomic team-file replacement), `which` (executable `PATH` lookup), `base64`, `thiserror`, `tracing`, `url` (host comparison for endpoint checks), `async-trait`, `libc` (unix only). `similar`, `notify`, `htmd` and the ripgrep search crates left with the tools that used them; `sha2` and `getrandom` left with the wires and the logins; `secrecy` stays a production dependency here for the one secret the engine itself holds, `mcp.rs`'s dial-time bearer.
