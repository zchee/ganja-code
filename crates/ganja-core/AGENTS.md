# ganja-core

## Purpose

The engine: session orchestration, the agent loop, and the state a conversation leaves behind. This crate carries **no terminal-backend dependency** — no `ratatui`, no `crossterm` — so the engine stays testable without a terminal and can later be driven over a network transport.

Four things it is built on are crates of their own — `ganja-protocol`, `ganja-permission`, `ganja-tool`, `ganja-provider` — and this crate re-exports each under the module name it always had, so `ganja_core::protocol`, `ganja_core::permission`, `ganja_core::project`, `ganja_core::tool`, `ganja_core::watch`, `ganja_core::auth` and `ganja_core::catalog` all keep resolving. The crate root names the engine's own types and nothing else; a caller that only wants one of the four should depend on it directly — the facade's module names are for the callers that want the engine.

`ganja_core::provider` is the one facade that is not a bare re-export. The wires left; the half that reads a `Config` — which provider a session runs as, which model it asks for — stayed, over a glob of the crate that took them. `src/AGENTS.md` says which functions are on which side.

**D557 — `/deadline`, a time budget the model is told about** (2026-09-11, `.omc/plans/2026-09-11-deadline-command.md`). A person who knows how long they have says so once, and the model is reminded on every step. `Command::SetDeadline { until: Option<u64> }` records an absolute instant on `Engine::deadline`, a `std::sync::Mutex<Option<SystemTime>>` in `permission_mode`'s shape with no guard across an await, and every request assembled while one is set carries one **request-only** user message at its tail — the same seam and the same `Message::request_only_user` marker D556's Dv-22 built for the `/team` guards block, appended after it — so it is never written to the transcript, never replayed, and never mistaken by a wire that remembers what it sent for a rewind. `session::deadline_block(remaining: Result<Duration, Duration>, until: SystemTime)` is the one place either wording is spelled, and both are byte-pinned by test.

- **Warning only, and the prose is what carries it.** Nothing cancels a turn, shortens a tool bound or refuses a prompt for a deadline: it is information the model reads, exactly as a tool result is (the session loop's own rule), and the person keeps every decision. The second wording therefore says *start nothing* and never *stop* — the engine stopped nothing, and a sentence claiming otherwise would be the model's only evidence about a cancellation that never happened. A test drives a turn past the instant and it completes, which is that claim under gate rather than in a comment.
- **Read at every step, not at the turn's start.** The cell is shared into `Turn::deadline` the way `settled_receipts` is, rather than copied, because the moment somebody is most likely to type `/deadline` is while watching a turn they have run out of time for — a snapshot taken at the start would answer one turn late. The block is rebuilt from the cell and the clock each step rather than taken once (deliberately *not* `take_blocks`' posture): a deadline is a standing fact whose value has changed by the next step, where a block that appeared once would be a reminder the model read twenty steps ago.
- **A delegated turn gets none.** `Turn::child` takes `Arc::default()`, the receipts' reason turned around: a subagent is one step inside the sitting rather than the sitting, and the parent has already read the budget and written the prompt that spends it. Telling a worker with no view of the whole to "start nothing" and report what remains would be the parent's answer to give, and the parent would then have to take it apart again.
- **`NewSession` clears it; nothing else does, and a resume does not carry one.** The one cell here that reads the *opposite* way from the permission posture two fields over: that one is what this engine runs as and nobody asked for it back, where a deadline was somebody saying how long *this* piece of work had. Held on the engine rather than the stored row, so "a resume does not carry it" costs no code.
- **Polled, never pushed.** `Engine::deadline() -> Option<SystemTime>` sits beside `rate_windows`/`served_model`, the D484/D485 shape, and the reason is `served_model`'s rather than symmetry: what a deadline element draws changes on every tick whether or not anything happened, because what moves is the clock. An event could only announce the two edges a frontend already sees by comparing two readings. The accessor hands back the **instant** and never the remaining time, so no reading can be stale by however long the caller held it.
- **One spelling of a span, and it is this crate's.** `session::spell_duration` is `pub` because the status bar's `deadline` segment calls it — the block the model reads and the segment the person reads are two views of one number, and a second formatter in the frontend would be a second thing to keep true. `2h13m`, `4m30s`, `45s`: the largest unit that is not zero and the next one down, rounded down throughout, because a budget that says `1m` with fifty-nine seconds left is claiming time that is not there. `until` prints as the **local** `HH:MM`, not the UTC the `<env>` block stamps a date with: `/deadline 10:00` means ten o'clock where the person is sitting, and quoting it back in another zone would read as the engine having misunderstood its one argument.
- **The wordings were measured rather than invented.** Two long-running sessions working under a wall-clock deadline were asked what changed, and what changed in both was the *selection* of work — each step judged against the critical path to a fixed stop condition, everything else recorded as a note, decisions already made taken with a doubt written down instead of a question asked, and the safety checks kept. That is why the first wording names the critical path and explicitly protects the checks: a deadline that read as "go faster" would buy time out of the one budget nobody wants it spent from.
- **`StatuslineElement::Deadline`** is the config half, `deadline` in a `tui.statusline` roster and on the default bar for `Held`'s reason rather than `TaskList`'s — a session with no deadline yields no segment, so the absent-config bar is unchanged cell for cell. It is on the default bar where `task-list` is not because reading it costs a clock subtraction where reading that one costs a directory read: an element nobody asked for may spend a comparison, never disk.

## For AI Agents

### Working In This Directory

- **The purity rule is the crate's reason to exist.** The root `depgate.toml` denies `ratatui*` (and `axum*`) from this crate's normal tree, gated in CI by `cargo depgate check`. Anything the UI must render is expressed as a serde type in `ganja-protocol`, never as a widget or a style.
- **The crates beneath this one may not name it.** Each is asserted as a closed allowlist of its own internal dependencies — the `internal` rules in the root `depgate.toml` — rather than a blocklist, which would go quiet the day a new crate appeared: `ganja-tool` is exactly `ganja-permission`, `ganja-provider` is exactly `ganja-permission ganja-protocol ganja-tool`, `ganja-team` and `ganja-storage` reach at most the two bottom leaves, and this crate's own set is exactly the six beneath it. A tool that appears to need something from the engine needs a value in its `ToolCtx` instead; a wire that appears to need one needs another field on its `ChatRequest`.
- **Everything on the protocol is serde-derived from day one.** That serialization constraint — not a trait — is what preserves the path to serving the engine and to persisted transcripts. A new field or variant should be considered wire-visible even though nothing serves it yet.
- The crate root's flat re-exports in `src/lib.rs` name the engine's own types only; a new core module that frontends use re-exports its types there alongside the rest, while a type that belongs to `ganja-protocol`, `ganja-permission`, `ganja-tool` or `ganja-provider` is reached through those module names, never flattened into the root. A frontend that only renders must be able to build against `ganja-protocol` alone, and a root that flattens protocol types into the engine's vocabulary invites the opposite.

### Testing Requirements

```sh
cargo nextest run -p ganja-core               # unit + integration, each test its own process
cargo nextest run --workspace permission      # tests whose name matches "permission", wherever they live
cargo nextest run -E 'binary(golden)'         # one integration binary
cargo test -p ganja-core --doc                # doctests, which nextest does not run
```

Unit tests live in `#[cfg(test)] mod tests` at the bottom of the module they cover; anything that needs a real socket, a real filesystem layout, or process-wide environment mutation lives in `tests/` instead.

### Common Patterns

- Errors are `thiserror` enums whose messages say what the caller can do about it; the taxonomies are deliberately transport-agnostic (`SelectionError` wraps `ganja-provider`'s `ProviderError` across the crate boundary, which is what `#[error(transparent)]` is for).
- Trait objects only where dyn-safety demands it: `Tool`, the subagent seam and (in `ganja-provider`) `Provider` live behind `Arc<dyn _>`, which is why `async-trait` is a dependency.
- Shared mutable state is `Arc<std::sync::Mutex<_>>` for short critical sections and `tokio::sync::Mutex` only where a lock is held across an `.await`. No lock is ever held across an await in a path the render loop depends on.

## Dependencies

### Internal

`ganja-protocol`, `ganja-permission`, `ganja-tool`, `ganja-provider`, `ganja-team` and `ganja-storage`, re-exported as modules from `src/lib.rs`. `ganja-tui` and `ganja-cli` depend on this crate, and additionally on the protocol, the permission crate, (for the frontend's `@` file menu) the tool crate and (for `auth login`) the provider crate, where they name those types directly.
