# ganja-core

## Purpose

The engine: session orchestration, the agent loop, and the state a conversation leaves behind. This crate carries **no terminal-backend dependency** — no `ratatui`, no `crossterm` — so the engine stays testable without a terminal and can later be driven over a network transport.

Four things it is built on are crates of their own — `ganja-protocol`, `ganja-permission`, `ganja-tool`, `ganja-provider` — and this crate re-exports each under the module name it always had, so `ganja_core::protocol`, `ganja_core::permission`, `ganja_core::project`, `ganja_core::tool`, `ganja_core::watch`, `ganja_core::auth` and `ganja_core::catalog` all keep resolving. The crate root names the engine's own types and nothing else; a caller that only wants one of the four should depend on it directly — the facade's module names are for the callers that want the engine.

`ganja_core::provider` is the one facade that is not a bare re-export. The wires left; the half that reads a `Config` — which provider a session runs as, which model it asks for — stayed, over a glob of the crate that took them. `src/AGENTS.md` says which functions are on which side.

The clause deliberately **not** taken is stripping this session's own marker: it reads as hygiene and is the loop check's own undoing, since the own-marker count climbs only because each forwarder leaves its marker behind — a session removing its own on every adoption would hold a two-cycle at constant length forever, and a chain carrying more than ten of them is already refused before adoption can see it. **Not ported, by argument at the site**: the reference's text envelope grammar, its attribute order and its canonical re-serialization check, because ganja's crossing is a JSON body whose analogue is `deny_unknown_fields` and whose text never becomes markup; the model-visible/control-plane split, for the stronger reason that the chain never enters prompt text at all, the model reading `PartBody::Peer` composed from `text` alone; and the `from-session` attribute, which the reference itself records both of its own call sites passing as undefined. **The parity matrix is reached by a never-loosen composition, not by flipping a flag**: `HONOR_SENDER_MODE` stays `false` as the floor, and the socket door asks `ResolvedInbound::decide` twice — once collapsed, once honored — and keeps the **stricter** of the two answers, ties taking the honored cause. Composed over `decide` and never over `decide_unset`, because `decide` resolves an explicit `cross_session_inbound` value in its first branch and composing beneath it would have silently broken that key. Exactly **one row moves**: a bypass sender into a prompting receiver now **holds** as `mode-mismatch` where it was delivered. One row is a **deliberate divergence** — `(bypass, bypass)` keeps ganja's hold where the reference accepts — because an unproven wire attestation may not do a credential's work at the widest-privilege receiver class, and the honored row's benefit is stated rather than oversold: a hostile same-uid sender simply asserts `prompting` and is treated exactly as before, so what this buys is misconfiguration hygiene between one user's own honest sessions, reviewable in the dialog, listed in `/held`, counted on the status bar and reported to the sending model on the POST itself. `SocketDelivered` grows exactly one field, `held`, carrying a hold's cause as a typed value and **present only on a hold** — absent for an accept *and* for a refuse, so those two answers stay byte-identical and D523's uniform answer is untouched; a typed field rather than sniffing the peer's own prose out of `note`, which is a `reflected()` display cut. Skew is stated in both directions: a new receiver reading an old sender's body falls to the two collapsed rows, which is exactly today's behavior, while an old sender parsing a new receiver's held answer refuses it as a failed send — true of **every** future additive field on that answer, which is why the note lives at the declaration and not in a review comment. **D534 — receipts.** A settlement rides back to a reply-capable sender over the socket's fourth route, and **only a held message's settlement ever does**. An accept emits nothing, a refuse emits nothing, a guard drop emits nothing — which is what keeps D523's byte-identical answer a structural property rather than an assertion: there is no receipt whose presence or absence could tell an accept from a refuse, because neither ever produces one. The *held* fact itself already shipped synchronously, in the answer to the very POST that was held, and the wire now says it with a typed field; an outstanding id is registered only when that answer said held **and** a reply address rode along, so silence on the receipt route means exactly one thing — still held — instead of a six-way ambiguity. The sender's registry holds at most 200 ids, evicted oldest-first and cleared by `NewSession`, and **trusts a receipt for nothing**: the id must be outstanding, any of the three statuses removes the entry (a second receipt for a settled id is a receipt for an unknown one), and the route answers identically admitted or dropped, so nobody may probe which ids a session is holding. What a forged receipt can do is lie about one known message's fate to the session that sent it; it cannot inject text — the poster supplies one enum value and every word the model reads is ganja's own rendering — cannot enqueue a turn, cannot touch permissions, and cannot reach an id it does not know. On the receiver's side a settlement is posted from **exactly three paths and no others**: a person releases, a person denies, or the `dialog_expiry` clock runs out — so `Expired` means the review window ran out and nothing else. A **capacity eviction emits nothing**, because `hold()` evicts with no person involved, at a rate and against targets an attacker chooses once the buffer is primed; the **shutdown drain emits nothing**, because it would burst the whole buffer at once to sender-chosen addresses inside a 750 ms teardown budget, and a crash settles nothing at all, so its presence would have said only "this peer exited politely" — a signal unreliable by construction. A sender those paths cannot reach is left *true and stale*, its last known state still held, which is exactly where a crash already leaves it. `reply_to` is vetted for **shape** and never for being the sender, so a receiver can be made to open one bounded outbound connection to an address a sender chose — named in the module's own doc rather than discovered later, and bounded by four things: one attempt per settlement and never a retry, only a person's decision or the review clock emitting one at all, `vet_address` confining the target to a `.sock` in this uid's own `0700` directory, and the third session answering an unknown id indistinguishably from an admitted one, so the reflection is not even a probe. **The guard moved ahead of the hold arm**, and that is this landing's one call-site reordering: the token bucket, the body dedup and both hop checks lived inside the accept arm alone, so holds could be generated at machine rate — and it is *this* landing that newly aims traffic there, since a sender asserting bypass now lands on hold where it used to land on a guarded accept. A post-landing security review found the hoist alone insufficient and it was closed the same day (**2026-08-27**): every limit the guard weighs is keyed on the peer's own claimed `from`, which is shape-checked and never authenticated, so a sender that rotated it drew a fresh bucket and a fresh dedup window per message and churned the review surface at machine rate anyway — the exact harm the hoist was for. The hold arm therefore consults a **second bucket, one for the whole door and keyed on nothing a wire carries**, on the guard's own two constants (a burst of thirty, then one per two seconds), ordered after the per-sender checks so an honest peer's own limits still answer first; its stated cost is that while an attacker is spending that bucket an honest peer's parity hold is dropped rather than reaching review, which is the trade the accept arm already makes and strictly better than the one it replaces, where the honest hold reached the buffer by evicting another. The hoist is **scoped by cause** to exactly the two parity causes that gained that traffic; an explicitly configured `cross_session_inbound: "hold"` and the fail-closed mode-unknown hold stay ungated, because a person who configured a hold asked for **every** message to reach review and the 30 s dedup would swallow a repeat silently in both directions — a configured value quietly delivering less than it names is the defect class a review pass exists to catch. The residual is declared rather than fixed: an explicit-hold user stays exposed to buffer churn, bounded by the cap, by the count on the status bar, and by the fact that an eviction now emits nothing at all. Keying a settlement back to its message costs one additive field — the admission returns the `HeldId` it minted — and the association from that id to the message id and the vetted reply address lives in the receipt module's own map rather than on the gate's buffer record, which is one of this landing's byte-untouched promises; a settlement arriving with no association posts nothing, the same silence every other unreachable case produces. A receipt reaches the person as one status-bar line and the model as one `<peer_receipt>`-tagged part batched at the next prompt intake, on D529's own vehicle and through one byte-pinned rendering — and the model-facing half is **ganja-inferred**, since the reference records that notice on the sender's own UI and does not say it reaches the model. **D533 — addressability, ruled down to its sentences.** The plan proposed widening the bind predicate to every interactive non-member session and building a receiving surface behind it for the session that leads no team. **None of that was built** (user ruling, 2026-08-27, answering the plan's own first open question with its (b) option). The ground is a trace the plan ran on itself and then had to act on: `config_home()` answers `None` only where `GANJA_CONFIG_HOME` is unset and `Xdg::new()` errs, and every shipped entry point hard-bails on that same call behind a `?` long before it could reach the arm that condition selects (the three sites are named at D530 above). So the arm the widening existed to serve is **structurally unreachable in every shipped binary**, and the surface would have been built for a code path that cannot execute. The bind predicate is therefore **unchanged**, no synthetic peer view or its handler exists, no recipient constant, no second receive ladder, no in-memory inbox and no second drain, and the one-way clauses on a teamless send stayed in the tree **and stayed true**, because the arm that would have made them false still bound nothing — **D542** then deleted that arm outright, leaving no shipped binary that reached the sentences, and **D543** deleted the sentences themselves: the session they described cannot be built here, since one leading nobody binds, registers and is addressable. What D533 delivered is three sentences and the decision behind them: `send_message`'s teamless description stopped claiming this build offers no listing tool and points at `list_sessions` instead; `ganja-cli`'s binder comment stopped claiming a lead-only decision the code never made, and now says plainly that the door is handed in unconditionally and that the gate behind it is `ganja-tui`'s own; and the finding itself is on the record here, together with the ruling not to build for a dead arm. Deleting that arm rather than filling it in was filed as a bead (`ganja-code-e99`) rather than acted on here, because it would have reopened D530; the user ruled that bead narrow on 2026-08-29 and **D542** deleted the arm, folding the bind predicate this decision left unchanged down to membership alone — the *sentences* D533 delivered are untouched by it, and what became of the machinery behind the arm is **D543** (2026-08-30): deleted, with the state it stood for derived from the registry instead. **Four execution-time deviations are part of the record.** (**Dv-1**) The plan's envelope id type `MessageId` collided with the conversation-message id of that name this tree has carried since D493, so it landed as `PeerMessageId` — a separate type on `HeldId`'s own precedent; every field name the plan specified is unchanged. (**Dv-2**) The new event and the new answer field forced mechanical completions in five files outside the owning wave — match arms and one `held: None` literal, behavior unchanged everywhere — on the one-mechanical-line precedent this file already records for the sender-side trio, and the not-yet-wired seam items carried a self-clearing `expect(dead_code)` marker until the wiring consumed them. (**Dv-3**) The sender-side receipt registration structurally lives inside `deliver_over_socket`, whose `Sent` cannot carry a message id out to any caller, so the wiring wave was granted a scoped seam on both postboxes — `with_receipts`, the `with_peer_facts` twin — plus the one register call after the POST. (**Dv-4**) The plan's letter had `sender_mode()` calling the engine's receiver classifier live, which is **unbuildable**: both postbox installers run before the engine is behind an `Arc`, so there is no weak handle to hold. It landed by sharing the permission-mode cell itself and calling the same classifier the engine calls — one function over one piece of state, nothing staleable, which is the property that was actually wanted, pinned by a full-cross-product wire test. Under the same deviation the expiry timer's receipt post is spawned out of the expiring task rather than awaited, because the settlement it reports aborts that task and an awaited post would be cancelled by its own subject, every time; one attempt, no retry and its own deadline are all kept. Two execution findings are recorded rather than smoothed over: the sender's 33-entry chain truncation is **unreachable through the engine's own doors** — a receiver refuses past 28, and since the same security review's §1 an adoption keeps at most 27, so the wire tops out at 28 — and its arithmetic is pinned at the facts level over a planted chain instead; and the matrix's self-sent row has **no production producer** in this build, there being no ancestry walk, so it stays unit-tested in the decider's own suite with the site saying why.
- `teammate/tasklist.rs` + the installers in `engine.rs` — **D546 (the engine half)**, the shared task list behind the four task tools (2026-09-02, `.omc/plans/2026-09-02-team-orchestration.md`, W3). `ganja-tool` may name only `ganja-permission`, so it cannot name the crate that owns a task document's format; the four tools decide what the model asked for and hand it across `ganja_tool::tasklist::TaskList`, and `TeamTasks` implements that over `ganja_team::task::Store` — the tool half is stated in full in `crates/ganja-tool/AGENTS.md`, the store in `crates/ganja-team/AGENTS.md` (**D545**). Three things are decided here and nowhere else. **Every call is wrapped in `spawn_blocking`**, because that store is deliberately synchronous and its own doc asks to be called that way: a lock held by another process is a wait, and a wait taken on the runtime's own thread would be a whole session's render loop waiting on somebody else's write. **The identity is bound at construction** — both constructors (`TeamTasks::new`, `TeamTasks::of`) take the name this session writes comments under and keep it, so no call can choose one — which is the postbox's rule for the postbox's reason. And **ownership settles first**: a claim is the operation two processes race for, so the order is the contract, and a call whose claim was refused leaves the task exactly as it was rather than announcing work its caller never got. Installation follows `send_message`'s **presence-is-ability** rule through three doors for the same three kinds of session — `Engine::with_teammates` for a lead, whose registry names the team the list belongs to; `Engine::with_tasks` for a pane teammate, whose frontend holds the teams root its lead wrote; `Engine::install_tasks` for an in-process teammate, whose name and team first exist together after its engine was built — and the four tools are offered wherever a list is installed and nowhere else, which is what keeps the golden differential comparing two agents rather than two teams. It is deliberately **not** gated on the team holding anybody (**Dv-5**): the pipeline files the work before it spawns whoever will do it, so a list withheld until the first member would be withheld at exactly the moment it is used first — exercised rather than argued by W3's pane drill, where a task is filed before any spawn, `tasks/` exists with no `config.json` beside it, and the registry later writes one into that same directory. **A subagent gets none of the four**, for the reason it gets no `send_message`: a delegated turn runs inside its parent's, and the identity it would claim and comment under is the parent's. The read side is one accessor, `Engine::task_list`, **read-through and `async` where its `team_view`/`held_messages` neighbours are neither** — the list is documents another process writes, so a cached count would be a count of what this session last did — answering `None` both where no list is installed and where the directory would not open, because what a status surface can honestly draw for either is nothing and a failure is traced rather than rendered.
- `command.rs`'s `/team` builtin, `agent.rs`'s five new roles and `teammate/discipline.rs` — **D547**, the team pipeline and the two guards under it (2026-09-02, `.omc/plans/2026-09-02-team-orchestration.md`, W4). **Provenance first, because it is the decision**: the pipeline's *shape* — a staged run that decomposes, spawns, coordinates through a shared list, verifies and fixes — is modelled on oh-my-claudecode's team skill, read as a behavioral reference; **every shipped text is ganja's own prose**, written from that plan's behavior specification rather than copied or edited from it, which is why oh-my-claudecode earns **no `THIRD_PARTY_NOTICES.md` entry**. That is **D497**'s posture applied to a second source: what is borrowed is idea-level and named honestly (the stage identifiers `team-plan`/`team-prd`/`team-exec`/`team-verify`/`team-fix`, the five handoff headings, the Task\* status vocabulary), and what would have been expression is not borrowed at all. `/team` is a builtin on **`/init`'s precedent**: a compiled-in template, `$ARGUMENTS`, and a model that parses the grammar — nothing here parses `[N[:agent]] [--backend <surface>] <task>`, because the whole command is prose the model acts on. Its **three** placeholders are filled by the code rather than described to the model, for the reason `/init` fills its worktree one: an instruction that says "write your state under the data home" is one every session guesses about, and two sessions that guess differently do not resume each other. The two directories are filled **at roster build** — both in the data home, since operational state lives there and `.ganja/` stays a committable-config namespace — with `replace` rather than `replacen`, because the handoffs placeholder appears twice and a survivor would reach the model as a literal `${handoffs}` nothing on the machine answers to. The third, `${session}`, is filled **per expansion** instead, and the split is what each one *is*: a directory is a fact about the checkout, the same for every session in it, while which session is running changes with every `NewSession`, every resume, and between two ganja processes in one worktree — one roster serves them all. It has to be filled at all because **a session cannot read its own id**: the `<env>` block does not carry it and `list_sessions` drops the caller's own row, so the template's original "use this session's own id" was asking for the one fact the model on the other side of it has no way to find out, and the file name is now given outright. It goes in **last of all**, after `$ARGUMENTS`, after the shell pass and after the mentions are resolved, which is a safety property rather than a taste: every pass that reads the text for something to *run* or *attach* has already finished, so nothing an id happens to spell can become a command this template executes. Five agents join the roster — `analyst`, `executor`, `verifier`, `critic`, `debugger`, taking it from four to nine — **subagent-mode and never a primary**, exactly what `general` and `explore` already are, and with **no rule delta at all**: a role here is a prompt, not a permission posture, and an executor that could not run what every other agent runs would be a different agent from the one its prompt describes; a project that wants a narrower one says so in `.ganja/agents/`, whose same-named definition outranks the builtin. Each prompt says what the role *is* and nothing about how a team coordinates, so the protocol has one home in the template and an agent spawned outside a team is still a coherent agent. **The two guards exist because neither can be a sentence in a prompt and still be true.** The template can ask the model to work the list until it is drained and to give continuing work a named teammate; what a prompt cannot do is notice when it stopped anyway. So the noticing is engine-native and made only of typed facts — a registry holding a live member, a task document still `pending` or `in_progress`, a `task` call whose arguments carry no `name` — and the state JSON the model writes for itself is **never consulted**, being exactly as reliable as the behavior it would be checking. The **continuation blocker** injects one block at the turn's tail and does it at most `MAX_CONTINUATIONS` = 5 times before handing the session back rather than talking to itself; it loses to a person every time — a steer is answered first and resets the budget, a cancel ends the loop before any of it is asked, and nothing is injected while a dialog is still waiting — **this turn's own or one a teammate forwarded** (bead `xysf`), because both land on the one screen the block would be talking over, and only the second of the two really happens: a teammate's turn runs beside the lead's, so its question can be raised after the model has stopped talking. The count is the registry's own (`TeammateRegistry::dialogs_waiting`), raised by the one door both carriers send through and given back by a guard the waiting side holds, so it cannot drift from what is on the screen. **A person's** steer, and only that: a teammate's message reaches the same mailbox as a `Steer` carrying an envelope and no text, keeps the turn going like any other drained message, and resets nothing — the traffic a live team generates is what the breaker is counting, so a team with something to say every step would otherwise refill the five forever; what that does not bound is the turn itself, which a team speaking every step keeps going one drained message at a time — nothing counts those, since the breaker counts what the model did on its own. The breaker is a **constant rather than a config key**, deliberately: what a person tunes when this annoys them is whether the team is running at all. Its counter lives on the **turn** rather than the engine, because "five consecutive auto-continuations" is exactly a turn's own count — the only way a sixth turn happens is that somebody prompted or steered, and either resets it — so there is no engine cell to clear on `NewSession` and no way for the two to disagree across a resume. The **name nag** sits one step earlier, scanning a step's whole batch of calls before any of them runs, which is what makes "once per assistant step" structural rather than a flag that happens to collapse: five anonymous `task` calls in one fan-out are one scan and one block. What makes a step one to nag about is **two** facts, either sufficient (bead `s8rw`): the registry holds somebody live at the moment of the scan, or the batch itself names somebody in a `task` call of its own. The second exists because the first cannot see the pipeline's own opening step, which spawns its named members in the very batch being scanned — the registry is empty however late it is read, so a registry-only trigger answered about the instant before the delegation it was supposed to be about, and the pipeline's own first step was the one step that could never be nagged. Reading the naming off the calls themselves takes the answer off the clock. It blocks nothing — an anonymous subagent stays first-class (**D462**), and a turn that leads nobody and names nobody is silent. **Both blocks belong to the request and never to the transcript**: a stored user part nobody typed would come back on the next resume as something they said. They are appended as a **user message of their own**, after the reply so far and after anything steered, rather than folded into the last user message the session reminders ride on — those answer a message somebody sent, these answer what the assistant just did. On the continue arm nothing was steered, so folding would put the instruction *before* the reply it is about and leave the request ending on the assistant's own text, which the Anthropic wire sends as a prefill and refuses outright when it ends in whitespace; appended, the shape is exactly a steer's. Two placements are rulings of their own (**Dv-6**): the blocker sits at the agent loop's own end — no tool calls, steers drained — rather than at `run_turn`'s tail, which is identical behavior with no engine re-entry plumbing and leaves the `Stop` hook firing once; and both guards read the team off a **field of the turn's** rather than through the spawn host, because that host holds the same registry but is absent on an engine with no agents, and whether a session was given an agent roster says nothing about whether it leads a team. Headless, the spelling is **`ganja run --auto --command team "…"`**, measured rather than assumed: `ganja run "/team …"` sends the text verbatim and expands nothing, while `--command` reaches the same expansion the TUI's typed line does — and `--auto` is not optional for a pipeline that gets anywhere, because its state file and its stage handoffs are written with `write`, which asks by default (`ganja_permission::ASK_BY_DEFAULT`), and a headless run answers every dialog it is not given `--auto` for with a refusal (`crates/ganja-cli/src/run.rs`); `write` is not one of the three that stay refused even then. Without it the run reads the template, files nothing, and reports refusals. One more refusal is the code's rather than the model's (bead `2m46`): `/team` given exactly `spawn …`, `shutdown …` or a bare `list` — `/teammate`'s own three subcommands after **D544**'s clean cut — is refused where the expansion would have begun, naming the line that was meant with `/teammate` in place of `/team`, so no turn starts and no round trip is spent having the model say what three fixed words already say. Deliberately only those spellings: `list` takes no arguments of its own, so `/team list the config keys` is a task and expands, and every other phrasing that means the same thing is still the template's second arm to answer.

## For AI Agents

### Working In This Directory

- **The purity rule is the crate's reason to exist.** The root `depgate.toml` denies `ratatui*` (and `axum*`) from this crate's normal tree, gated in CI by `cargo depgate check`. Anything the UI must render is expressed as a serde type in `ganja-protocol`, never as a widget or a style.
- **The crates beneath this one may not name it.** Each is asserted as a closed allowlist of its own internal dependencies — the `internal` rules in the root `depgate.toml` — rather than a blocklist, which would go quiet the day a new crate appeared: `ganja-tool` is exactly `ganja-permission`, `ganja-provider` is exactly `ganja-permission ganja-protocol ganja-tool`, `ganja-team` and `ganja-storage` reach at most the two bottom leaves, and this crate's own set is exactly the six beneath it. A tool that appears to need something from the engine needs a value in its `ToolCtx` instead; a wire that appears to need one needs another field on its `ChatRequest`.
- **Everything on the protocol is serde-derived from day one.** That serialization constraint — not a trait — is what preserves the path to serving the engine and to persisted transcripts. A new field or variant should be considered wire-visible even though nothing serves it yet.
- The crate root's flat re-exports in `src/lib.rs` name the engine's own types only; a new core module that frontends use re-exports its types there alongside the rest, while a type that belongs to `ganja-protocol`, `ganja-permission`, `ganja-tool` or `ganja-provider` is reached through those module names, never flattened into the root. A frontend that only renders must be able to build against `ganja-protocol` alone, and a root that flattens protocol types into the engine's vocabulary invites the opposite.

### Testing Requirements

```sh
cargo nextest run -p ganja-core               # unit + integration, each test its own process
cargo nextest run --workspace permission      # tests whose name matches "permission", wherever they live
cargo nextest run -E 'binary(golden)'         # one integration binary
cargo test -p ganja-core --doc                # doctests, which nextest does not run
```

Unit tests live in `#[cfg(test)] mod tests` at the bottom of the module they cover; anything that needs a real socket, a real filesystem layout, or process-wide environment mutation lives in `tests/` instead.

### Common Patterns

- Errors are `thiserror` enums whose messages say what the caller can do about it; the taxonomies are deliberately transport-agnostic (`SelectionError` wraps `ganja-provider`'s `ProviderError` across the crate boundary, which is what `#[error(transparent)]` is for).
- Trait objects only where dyn-safety demands it: `Tool`, the subagent seam and (in `ganja-provider`) `Provider` live behind `Arc<dyn _>`, which is why `async-trait` is a dependency.
- Shared mutable state is `Arc<std::sync::Mutex<_>>` for short critical sections and `tokio::sync::Mutex` only where a lock is held across an `.await`. No lock is ever held across an await in a path the render loop depends on.
