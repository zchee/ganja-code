# ganja-tool

## Purpose

What the model can do besides talk: `read`, `edit`, `write`, `glob`, `grep`, `bash`, `todowrite`, `webfetch`, `task`, `send_message`, the `Tool` trait they implement, the `Registry` that offers them, and the read-before-write log every one of them answers to. The stale-read watcher lives here too, because what it reports is a state on that log. So does `socket.rs`, which is not a tool at all but the one spelling of what a session socket is (**D505**) — four readers at four heights of the tree need that answer, and this crate is the lowest of them.

Its own crate for one reason, and it is the reason worth stating: **the engine is not in this crate's dependency graph, and never may be.** A tool answers to the rules and to the filesystem, never to the loop that called it. That used to be a convention a reviewer had to keep holding; now it is the compiler's rule, and a `use ganja_core::…` here does not build.

## Architecture

Hoisted out of the workspace root's `AGENTS.md` so that file stays inside Claude Code's 150,000-character context budget. The root keeps a summary and points here; this is where these decisions are stated in full.

**`ganja-tool`** — `Tool` trait + `Registry::with_builtins()` (read, edit, write, glob, grep, `bash`, todowrite, webfetch, `websearch` — Exa or Parallel over one JSON-RPC POST, keys from the environment, refused politely without one — `skill`, a `SKILL.md` under one of ganja's own two homes — `<config home>/skills` and `<project root>/.ganja/skills` — or a directory `skills.paths` named, loaded into the conversation on request; **nothing foreign is discovered**, a standing ruling that leaves upstream's `~/.claude`, `~/.agents` and their walk-ups unread and one config line away, and `question`, the one tool whose whole purpose is to wait for a person), plus `task`, which the engine registers once it knows which agents this session may spawn, and the two plan doors — `plan_exit`, registered once the roster holds a build agent, and `plan_enter`, its mirror, registered once it holds a plan agent and synthesized rather than ported because upstream ships that door's description and permission vocabulary and no tool body at all (**D477**). P24 added `deferral.rs` (**D492**, no upstream counterpart — the model is Claude Code's ToolSearch): the `Deferral` value — whole servers' `mcp__*` names advertise-filtered largest-first past the config's `tool_defer_threshold`, activated names exempt before the arithmetic, one order-preserving `retain_advertised` filter, and the per-step `<deferred_tools>` listing — plus the resident `tool_search`, which fetches a deferred schema by batch `select:` name or nucleo keyword and activates what it returns for the session; the registry itself stays complete, and a direct call to a deferred tool executes and activates by executing. The roster's `skill` holds no directories at all — where ganja keeps its things is not a question a tool may answer — so each of the three real frontends installs one over it holding `instruction::skill_roots`, the same value its prompt's `<available_skills>` block was composed from; a registry a *fixture* builds stays rootless, which is what keeps the golden differential comparing two agents rather than two laptops. Schemas generated from the argument structs; `FileTimes` enforces read-before-write; glob/grep run in-process on the ripgrep crates. `write` and `edit` reach the disk through a directory descriptor (`anchor.rs`), never twice through a path, so a link swapped in after the permission dialog has nothing to redirect. `watch.rs` is here too, beside the log it reports into. P25 added two more: `send_message` (**D498**), the one teammate-to-teammate door, registered by the engine only where a team exists — its sender is bound *inside* the `Postbox` in its `ToolCtx` rather than taken as an argument, so nobody can send as somebody else — and which runs **unasked**, because sending words is conversation and whatever the recipient does with them is gated by the recipient's own rules; and `socket.rs` (**D505**), which is not a tool at all but the one spelling of **what a session socket is** — `/tmp/ganja-<uid>/<8+ hex>.sock`, the `0700`-directory predicate, and the `vet_address` clauses a `uds:` address is refused by name against. Four readers at four heights need that answer (the tool at §5.2's rung 3, the engine's deliver arm, `ganja-serve`'s binder, `ganja sessions --live`) and this crate is the lowest of the four, so it is written here once and re-exported upward. **Nothing that binds moved**: the name walk, the liveness lock and the peer-uid check on accept stay in `ganja-serve/src/socket.rs`, and the allowlist is unchanged at `ganja-permission `. P27 hoisted one more answer down here, `prepare_directory` — the `0700`-directory predicate made real — because the shim orphan records live in that same `/tmp/ganja-<uid>/` and a second implementation of "is this directory ours" is a second thing to get wrong; that **amends D505's scheme/binder split** (**D509**) so the scheme crate now makes the directory and the binder keeps everything about a name. It depends on `ganja-permission` and on nothing else of ours — the engine is deliberately outside its graph, so a tool that seems to need the loop is a tool that needs another value in its `ToolCtx`. The sender-side trio put one more spelling here for D505's own lowest-reader reason: `registry.rs` (**D527**) is the registration record a lead session writes beside its bound socket — `/tmp/ganja-<uid>/<stem>.json`, the stem the bound socket's own, so record↔socket↔session correlate by filename and the record's liveness *is* the socket's flock (probed by a `try_lock`-and-drop on the new `socket::open_lock` primitive; the probe never unlinks) — carrying a **self-asserted** name that never authenticates anything: `--name`'s or `/rename`'s value, else the project root's basename through the one sanitizer, every grammar clause refused by name (no whitespace, ≤64 code points, none of `*`/`@`/`:`/leading-`/`/controls, no `#<digits>`/`#<digits>-<digits>` tail — each would collide with a send or mention grammar already in the tree; the tail clause is the strict review's find, the shape the `@`-mention scanner strips as a line range). Registration never refuses a collision (**user-ratified 2026-08-26**): a duplicate name is a notice naming the holder, and *resolution* is what refuses, which is D528's business. Reads are tolerant and size-capped with a `format` gate; writes are atomic through a dot-led staging name the listing walk can never read; the shared case-fold predicate (`same_name`, ASCII-only, the rung-8 precedent) is the one spelling collision scan, resolver and menu dedup all compare through. `team.rs` grew the two refusal kinds that resolution answers with — `Undelivered::{Ambiguous, NameMoved}`, `reason`-carrying like their siblings — and `send_message` grew a teamless description variant plus a team-agnostic `UNKNOWN_RECIPIENT` (the old sentence claimed a team every session no longer has); the eight rungs, `parse_address` and `vet_address` are byte-untouched, and the rung-0 rule now reads: registration follows the *postbox*, not the team (**D530**). The closing landing put one more model-facing surface here, `list_sessions.rs` (**D535**): a resident, argument-free tool answering one formatted listing rather than raw records, in two labeled sections. **Teammates** comes off the `Postbox` roster this crate already exposes, with the lead marked exactly as that roster marks it — and the section is **left out rather than printed empty** where the roster is, since a roster cannot itself tell a lead of nobody from a session with no team and a header over nothing would claim a team that may not exist. **Live sessions** comes off `registry.rs`'s own records — `list`, this session's own record dropped, then the `is_live` probe on every remaining stem: `holders`' composition minus its name filter, whose absence is a priced cost rather than an avoided one, since `is_live` *creates* the `.lock` it opens (never removed) and this walk therefore probes every other record and leaves one beside each stale record it judges — the price, stated in the module doc, of listing every live session rather than one name's collisions; this session is excluded, so is a stale lock-free record, and every row prints its name, its stem, its launch directory and its exact `uds:` spelling — which is what makes "a duplicate name shows its stem" true of every row rather than a special case, on D528's own ratified disambiguator. Each live row carries the label the mention reminder carries on the same bytes — a session's name is that session's own choice and nothing verifies it — and registry text is neutralized before it is rendered, the rule reproduced locally rather than shared because this crate's internal list is asserted to be exactly `ganja-permission ` and the reminder's own neutralization lives above it. Liveness is the **resolver's** vocabulary and not the CLI lister's: the lock probe alone, the same test the resolver re-applies the moment a model addresses a row this tool printed, because this crate may not link `ganja-client` to dial a session and a tool that opened a connection to every session on the machine at model cadence is a cost nobody priced — the honest consequence, that a bound but wedged session lists as live, is in the tool's own description rather than hidden. It runs **unasked**, on the argument that `read` and `glob` are unasked and can already read `/tmp/ganja-<uid>/*.json` directly, so an ask would gate a formatted view of data the model can already fetch unformatted; a deny rule still denies. **Where the engine registers it is deliberately not where `send_message` is registered**: that tool is offered on postbox presence alone, this one only where the installed postbox can actually **cross a session** — so a pane member, whose `MemberPostbox` refuses `Address::Uds` outright and resolves a name only against its own team file, keeps `send_message` and is offered no listing, because handing it a directory of addresses it structurally cannot use is exactly the noise the pairing rule was written against; a member that wants to know who else is running asks its lead, the road its permission dialogs already take. The excluded session id is read at composition rather than held from assembly, so a `NewSession` that re-mints the id cannot leave the tool listing its own session. `send_message`'s teamless description narrowed to match (**D533**): the clause claiming this build offers no listing tool is gone and points at `list_sessions` instead. Its one-way clauses stayed, and stayed true — vacuously so under **D542** (2026-08-29), which left no shipped session selecting the teamless description at all — until **D543** (2026-08-30, stated in full in `crates/ganja-core/AGENTS.md`) made "teamless" a live read of the session's own registry: the description is now what every session that has spawned no teammate really reads, that session binds a socket and registers a name, and so the text names the road back instead of being silent about it — appended per session rather than written into the constant, since a frontend binds that socket after assembly and `ganja run` binds none, so the sentence is added exactly where `Engine::peer_address` says one is bound. The roster/description distinction D530 drew is untouched — a team of one still lists "nobody yet" and must not read alike.

**D546 (the tool half) — the four doors a model drives a team's shared list through** (2026-09-02, `.omc/plans/2026-09-02-team-orchestration.md`, W3; `src/tasklist.rs`). `task_create`, `task_update`, `task_list` and `task_get`. **Neither upstream has a counterpart to port**: opencode has no teams, so it has nothing for two agents to divide between them, and Claude Code has a task list but keeps it inside its own process. What is taken from the latter is the *semantics a model is already trained on* — the status vocabulary, an owner empty until somebody claims it, a metadata map that merges, comments that only grow — and every sentence a model reads here is ganja's own, written from that plan's behavior specification.

**Keeping a list is not something a tool knows how to do**, and this crate could not learn: its internal dependency list is asserted to be exactly `ganja-permission`, so it may not name the crate that owns the documents' format (**D545**). So the four decide what the model asked for and hand it across `tasklist::TaskList`, whose implementation is the engine's — the same seam `send_message` reaches a mailbox through (`tool::team::Postbox`), for the same reason, and what crosses it is values while a directory, a lock protocol and a counter stay beyond it. Three mappings are settled on **this** side, because each is about what the model *asked for* rather than about how a document is written: a `status` of `deleted` is not a status but a removal (`TaskList::delete`), since the list carries three states and a deleted task is gone rather than tombstoned; an `owner` chooses between claiming and releasing (`Owner`), because a claim is the one operation that can be refused and a release never is; and **a comment's author is never an argument** — it is bound where the seam is built, exactly as a postbox's sender is, because a `from` parameter would be a fact about what the caller typed and the caller is a model whose arguments could put somebody else's name on what it said. A removal that travels with any other change is refused rather than half-applied: nothing is left for a new subject to be the subject of, and silently dropping the rest would leave the model believing it wrote something that was never written. `add_blocks` and `add_blocked_by` are the mirror case and are settled on the **other** side: the list records each dependency on both tasks (**D545**), so `task_update`'s own words say so and say that an id naming no task refuses the whole call — the model reads a refusal it can act on rather than a listing that goes on calling the other task free. Those words also carry the store's cap of eight counterparts per call and say the call is refused rather than truncated, because a bound the model is not told about reads to it as an arbitrary failure. That number is necessarily spelled twice — the store's own `MAX_COUNTERPARTS` and this crate's mirror of it beside the description, the allowlist forbidding the original be named — so the two are held to one decision from `ganja-core`, the one crate that sees both: an equality assertion beside a seam test that accepts eight counterparts and refuses nine, so raising either number alone reddens. The prose spells it in words and cannot format an integer, so it is pinned to the mirror by a test here rather than derived from it. `owner` is deliberately **not** bound to the caller the way a comment's author is (user ruling, 2026-09-02): a lead's pre-assignment has to name somebody else, the team is one trust domain, and the semantics are Claude Code's own TaskUpdate, which is what a model is already trained on — so what a call may choose is who holds a task, and what it may never choose is who said something. It is **trimmed at the claim**, in `change_of`, because the trim already decided the branch: whitespace alone is a release, so whitespace around a name is that member rather than a second one no later claim or release could name back. **A listing's rows are somebody else's words**, and one line is one task — so a subject carrying a newline would not be a subject with a newline in it, it would be two rows, the second a task nobody filed — which is answered by `list_sessions`'s own `neutralize` rather than by a second copy of it: same provenance, same one-row-per-line surface, same rule, and the crate boundary already costs one copy of it (`ganja-core`'s, which this crate may not name), where a second inside one crate would be a spelling to keep in step for no boundary at all. The id, the status and the blocker ids are the store's own closed vocabulary and are left alone. A call's **title** is the argument that says which task it is about — a `task_id`, or for `task_create` the subject it has instead of one — with absent and empty the same case, since a schema a model fills field by field produces `""` as readily as it omits the key and both leave nothing to head a transcript row or a permission dialog with; the tool's own name is then the whole title, never its name and a trailing space. And `UNOWNED` is `pub`: the model's listing is not the only surface that renders an empty owner — `ganja-tui`'s Tasks section says the same word in the same column — and a second spelling of it would let the two drift about what an unclaimed task looks like.

**What a member wrote is bounded before anybody reads it**, and the strict review's own pass over this module (2026-09-03) found three places it was not. **The two reading doors answer through `truncate::clamp`** — `task_get`'s pretty-printed record and `task_list`'s rows — exactly as `read`, `websearch` and `webfetch` do and with their spill file, because nothing between these tools and the documents bounds a description or a comment thread: the store's only bound is on a whole document and it is a megabyte, so one `task_get` could otherwise spend a context window with no file to recover it from, `clamp` being what creates one. Both reading doors carry `shell.rs`'s spill seam with them (`ShellTool::spill_dir`) — a directory only a `#[cfg(test)]` constructor ever names, `None` in every shipped build — because that spill file is the half a test cannot otherwise reach: left to resolve its own directory, a test of the clamp writes the whole pre-clamp text into a real person's `~/.local/share`, and on a machine where neither candidate is writable it passes on the pathless notice with no file written at all, which is the same green either way. `truncate::clamp_with` is `pub(crate)` rather than `#[cfg(test)]` for the reason `open_spill_in` already was: the `Option` no shipped constructor fills is what gates it, not the `cfg`. The **carried** record is deliberately left whole — the transcript part that persists it and the `PostToolUse` payload that is handed it are not spending a window on it — so the clamp is about what the model reads and nothing else; the two writing doors need none of it, answering with one summary line they built themselves. **`neutralize` widened past `Cc`**: `char::is_control` is that category alone, which left U+2028/U+2029 — line breaks to anything counting rows — and the bidi overrides, isolates and marks, which reorder what is drawn after them, so a subject could visually rewrite the row it is on while `lines().count() == 1` went on passing. That gap was pre-existing on the registry surface and largely covered there by `vet_name`'s refused grammar; a task subject goes through no grammar at all, which is what carried it onto a surface with far wider input. It is fixed in `neutralize` rather than beside it, on the same one-spelling argument that put the tasklist on that function to begin with. And **a call's title is cut at `shell::DESCRIBE_LIMIT`, through `shell::shorten`** — both widened to `pub(crate)` for `neutralize`'s reason — since a subject is free text under no length bound anywhere and an uncapped one is a transcript row and a permission heading the size of a document; a shell command was simply the first free text a description line was built from, not the last. Two model-facing sentences were qualified in the same pass: an id is "not reissued while this team's counter stands" rather than never reused, which is what the store actually guarantees (a counter rebuilt after loss can reissue an id deleted above the highest survivor, and that limit is pinned by the store's own test), and `task_update` now says that whoever holds a task counts as somebody **including you** — `Store::claim` refuses on `is_owned()` regardless of who asks, and the seam settles ownership first and returns before writing anything else, so a member repeating its own name on a follow-up loses the status and the comment travelling with it. `task_get` also says that the record reads back in a spelling its own arguments do not take (`activeForm` read, `active_form` written), because a model round-tripping a field writes the spelling it just read.

**They run unasked.** None of the four is in `ASK_BY_DEFAULT`, which is `todowrite`'s answer and for `todowrite`'s reason: what changes is a list this session's own team keeps inside a directory this user already owns, whatever a member goes on to *do* about a task is gated by that member's own rules, and the permission that mattered was answered at the spawn that made the team. A deny rule still denies. The no-list sentence (`NO_LIST`) sits at the **seam-absent arm**, which a normally assembled session reaches only in the window between a teammate's tools being lent and its list being installed — the engine lends the four with the rest of that roster and the spawn installs the list a moment later — so the sentence names a wiring fault rather than telling the model to go and make a team, which is `task`'s own `NO_TEAM` precedent, and is the narrowed reading the execution ledger's **Dv-5** settled: the pipeline files its tasks *before* it spawns whoever will do them, so a lead leading nobody must be able to create one. The `ToolCtx` gained one field for all of it, `tasks`, which is why every crate that builds one carries a mechanical `tasks: None,` completing an exhaustive literal (**Dv-4**). The **glossary** is load-bearing enough to be a module name: `task.rs` is the spawn door, always spelled *the `task` tool*, and `tasklist.rs` is the list — the two never mean each other, which is also why the status element the frontend draws is `task-list` rather than `tasks` (**D548**).

## For AI Agents

### Working In This Directory

- **The dependency direction is the point.** This crate depends on `ganja-permission` (which calls are gated, and the project root a write is checked for containment against) and on nothing else of ours. If a tool appears to need something from the engine, what it actually needs is a value in `ToolCtx` — that type is a bag of values rather than a handle back to a session precisely so this stays true.
- **The engine still owns *when*, not *how*.** It constructs the watcher through this crate's API and registers `task` into the registry once it knows which agents a session may spawn. Neither decision is reachable from in here, and neither should become so.
- **`ToolCtx` grows by value, never by handle.** A new thing a tool needs from its caller is a path, an id, a token or a trait object the caller implements — the credential-store path and the `Subagents` seam are both shaped that way on purpose.
- **A widened item is a claim about a reader.** `shell::{Progress, run_reporting}` and `task::{DESCRIPTION, ROSTER_HEADER}` are `pub` because the engine's `!` passthrough and its subagent module sit in another crate now. `anchor` stays a private module: it is how `write` and `edit` reach the disk, not something a frontend or a third-party tool has any business addressing files through.

### Testing Requirements

```sh
cargo test -p ganja-tool                      # the in-module suites, which travelled with the files
cargo nextest run --workspace                 # and the engine's, which drive these through a turn
cargo depgate check --config depgate.toml     # the boundary, asserted from the repository root
```

The last one reads the root `depgate.toml`, whose `ganja-tool` rule closes this crate's internal set at exactly `ganja-permission` — an exact-set allowlist that fails closed, where a `! grep ganja-core` would go quiet the day a new internal crate appeared.

### Common Patterns

Every dependency is `x.workspace = true`; versions live in the root manifest with their rationale. Where a feature is enabled at the member level (`tokio-util = { workspace = true, features = ["rt"] }`), the comment says why this crate opts into that module.
