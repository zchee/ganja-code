# ganja-tool

## Purpose

What the model can do besides talk: `read`, `edit`, `write`, `glob`, `grep`, `bash`, `todowrite`, `webfetch`, `task`, `send_message`, the `Tool` trait they implement, the `Registry` that offers them, and the read-before-write log every one of them answers to. The stale-read watcher lives here too, because what it reports is a state on that log. So does `socket.rs`, which is not a tool at all but the one spelling of what a session socket is (**D505**) — four readers at four heights of the tree need that answer, and this crate is the lowest of them.

Its own crate for one reason, and it is the reason worth stating: **the engine is not in this crate's dependency graph, and never may be.** A tool answers to the rules and to the filesystem, never to the loop that called it. That used to be a convention a reviewer had to keep holding; now it is the compiler's rule, and a `use ganja_core::…` here does not build.

## Architecture

Hoisted out of the workspace root's `AGENTS.md` so that file stays inside Claude Code's 150,000-character context budget. The root keeps a summary and points here; this is where these decisions are stated in full.

**`ganja-tool`** — `Tool` trait + `Registry::with_builtins()` (read, edit, write, glob, grep, `bash`, todowrite, webfetch, `websearch` — Exa or Parallel over one JSON-RPC POST, keys from the environment, refused politely without one — `skill`, a `SKILL.md` under one of ganja's own two homes — `<config home>/skills` and `<project root>/.ganja/skills` — or a directory `skills.paths` named, loaded into the conversation on request; **nothing foreign is discovered**, a standing ruling that leaves upstream's `~/.claude`, `~/.agents` and their walk-ups unread and one config line away, and `question`, the one tool whose whole purpose is to wait for a person), plus `task`, which the engine registers once it knows which agents this session may spawn, and the two plan doors — `plan_exit`, registered once the roster holds a build agent, and `plan_enter`, its mirror, registered once it holds a plan agent and synthesized rather than ported because upstream ships that door's description and permission vocabulary and no tool body at all (**D477**). P24 added `deferral.rs` (**D492**, no upstream counterpart — the model is Claude Code's ToolSearch): the `Deferral` value — whole servers' `mcp__*` names advertise-filtered largest-first past the config's `tool_defer_threshold`, activated names exempt before the arithmetic, one order-preserving `retain_advertised` filter, and the per-step `<deferred_tools>` listing — plus the resident `tool_search`, which fetches a deferred schema by batch `select:` name or nucleo keyword and activates what it returns for the session; the registry itself stays complete, and a direct call to a deferred tool executes and activates by executing. The roster's `skill` holds no directories at all — where ganja keeps its things is not a question a tool may answer — so each of the three real frontends installs one over it holding `instruction::skill_roots`, the same value its prompt's `<available_skills>` block was composed from; a registry a *fixture* builds stays rootless, which is what keeps the golden differential comparing two agents rather than two laptops. Schemas generated from the argument structs; `FileTimes` enforces read-before-write; glob/grep run in-process on the ripgrep crates. `write` and `edit` reach the disk through a directory descriptor (`anchor.rs`), never twice through a path, so a link swapped in after the permission dialog has nothing to redirect. `watch.rs` is here too, beside the log it reports into. P25 added two more: `send_message` (**D498**), the one teammate-to-teammate door, registered by the engine only where a team exists — its sender is bound *inside* the `Postbox` in its `ToolCtx` rather than taken as an argument, so nobody can send as somebody else — and which runs **unasked**, because sending words is conversation and whatever the recipient does with them is gated by the recipient's own rules; and `socket.rs` (**D505**), which is not a tool at all but the one spelling of **what a session socket is** — `/tmp/ganja-<uid>/<8+ hex>.sock`, the `0700`-directory predicate, and the `vet_address` clauses a `uds:` address is refused by name against. Four readers at four heights need that answer (the tool at §5.2's rung 3, the engine's deliver arm, `ganja-serve`'s binder, `ganja sessions --live`) and this crate is the lowest of the four, so it is written here once and re-exported upward. **Nothing that binds moved**: the name walk, the liveness lock and the peer-uid check on accept stay in `ganja-serve/src/socket.rs`, and the allowlist is unchanged at `ganja-permission `. P27 hoisted one more answer down here, `prepare_directory` — the `0700`-directory predicate made real — because the shim orphan records live in that same `/tmp/ganja-<uid>/` and a second implementation of "is this directory ours" is a second thing to get wrong; that **amends D505's scheme/binder split** (**D509**) so the scheme crate now makes the directory and the binder keeps everything about a name. It depends on `ganja-permission` and on nothing else of ours — the engine is deliberately outside its graph, so a tool that seems to need the loop is a tool that needs another value in its `ToolCtx`. The sender-side trio put one more spelling here for D505's own lowest-reader reason: `registry.rs` (**D527**) is the registration record a lead session writes beside its bound socket — `/tmp/ganja-<uid>/<stem>.json`, the stem the bound socket's own, so record↔socket↔session correlate by filename and the record's liveness *is* the socket's flock (probed by a `try_lock`-and-drop on the new `socket::open_lock` primitive; the probe never unlinks) — carrying a **self-asserted** name that never authenticates anything: `--name`'s or `/rename`'s value, else the project root's basename through the one sanitizer, every grammar clause refused by name (no whitespace, ≤64 code points, none of `*`/`@`/`:`/leading-`/`/controls, no `#<digits>`/`#<digits>-<digits>` tail — each would collide with a send or mention grammar already in the tree; the tail clause is the strict review's find, the shape the `@`-mention scanner strips as a line range). Registration never refuses a collision (**user-ratified 2026-08-26**): a duplicate name is a notice naming the holder, and *resolution* is what refuses, which is D528's business. Reads are tolerant and size-capped with a `format` gate; writes are atomic through a dot-led staging name the listing walk can never read; the shared case-fold predicate (`same_name`, ASCII-only, the rung-8 precedent) is the one spelling collision scan, resolver and menu dedup all compare through. `team.rs` grew the two refusal kinds that resolution answers with — `Undelivered::{Ambiguous, NameMoved}`, `reason`-carrying like their siblings — and `send_message` grew a teamless description variant plus a team-agnostic `UNKNOWN_RECIPIENT` (the old sentence claimed a team every session no longer has); the eight rungs, `parse_address` and `vet_address` are byte-untouched, and the rung-0 rule now reads: registration follows the *postbox*, not the team (**D530**). The closing landing put one more model-facing surface here, `list_sessions.rs` (**D535**): a resident, argument-free tool answering one formatted listing rather than raw records, in two labeled sections. **Teammates** comes off the `Postbox` roster this crate already exposes, with the lead marked exactly as that roster marks it — and the section is **left out rather than printed empty** where the roster is, since a roster cannot itself tell a lead of nobody from a session with no team and a header over nothing would claim a team that may not exist. **Live sessions** comes off `registry.rs`'s own records — `list`, this session's own record dropped, then the `is_live` probe on every remaining stem: `holders`' composition minus its name filter, whose absence is a priced cost rather than an avoided one, since `is_live` *creates* the `.lock` it opens (never removed) and this walk therefore probes every other record and leaves one beside each stale record it judges — the price, stated in the module doc, of listing every live session rather than one name's collisions; this session is excluded, so is a stale lock-free record, and every row prints its name, its stem, its launch directory and its exact `uds:` spelling — which is what makes "a duplicate name shows its stem" true of every row rather than a special case, on D528's own ratified disambiguator. Each live row carries the label the mention reminder carries on the same bytes — a session's name is that session's own choice and nothing verifies it — and registry text is neutralized before it is rendered, the rule reproduced locally rather than shared because this crate's internal list is asserted to be exactly `ganja-permission ` and the reminder's own neutralization lives above it. Liveness is the **resolver's** vocabulary and not the CLI lister's: the lock probe alone, the same test the resolver re-applies the moment a model addresses a row this tool printed, because this crate may not link `ganja-client` to dial a session and a tool that opened a connection to every session on the machine at model cadence is a cost nobody priced — the honest consequence, that a bound but wedged session lists as live, is in the tool's own description rather than hidden. It runs **unasked**, on the argument that `read` and `glob` are unasked and can already read `/tmp/ganja-<uid>/*.json` directly, so an ask would gate a formatted view of data the model can already fetch unformatted; a deny rule still denies. **Where the engine registers it is deliberately not where `send_message` is registered**: that tool is offered on postbox presence alone, this one only where the installed postbox can actually **cross a session** — so a pane member, whose `MemberPostbox` refuses `Address::Uds` outright and resolves a name only against its own team file, keeps `send_message` and is offered no listing, because handing it a directory of addresses it structurally cannot use is exactly the noise the pairing rule was written against; a member that wants to know who else is running asks its lead, the road its permission dialogs already take. The excluded session id is read at composition rather than held from assembly, so a `NewSession` that re-mints the id cannot leave the tool listing its own session. `send_message`'s teamless description narrowed to match (**D533**): the clause claiming this build offers no listing tool is gone and points at `list_sessions` instead, while its one-way clauses stay — and stay true.

## For AI Agents

### Working In This Directory

- **The dependency direction is the point.** This crate depends on `ganja-permission` (which calls are gated, and the project root a write is checked for containment against) and on nothing else of ours. If a tool appears to need something from the engine, what it actually needs is a value in `ToolCtx` — that type is a bag of values rather than a handle back to a session precisely so this stays true.
- **The engine still owns *when*, not *how*.** It constructs the watcher through this crate's API and registers `task` into the registry once it knows which agents a session may spawn. Neither decision is reachable from in here, and neither should become so.
- **`ToolCtx` grows by value, never by handle.** A new thing a tool needs from its caller is a path, an id, a token or a trait object the caller implements — the credential-store path and the `Subagents` seam are both shaped that way on purpose.
- **A widened item is a claim about a reader.** `shell::{Progress, run_reporting}` and `task::{DESCRIPTION, ROSTER_HEADER}` are `pub` because the engine's `!` passthrough and its subagent module sit in another crate now. `anchor` stays a private module: it is how `write` and `edit` reach the disk, not something a frontend or a third-party tool has any business addressing files through.

### Testing Requirements

```sh
cargo test -p ganja-tool                      # the in-module suites, which travelled with the files
cargo nextest run --workspace                 # and the engine's, which drive these through a turn
! cargo tree -p ganja-tool -e normal | grep -q ganja-core   # the boundary, asserted
```

The last one is inverted for the same reason the core-purity gate is: a plain `grep -c` exits non-zero on *zero* matches, and would fail exactly when the boundary holds.

### Common Patterns

Every dependency is `x.workspace = true`; versions live in the root manifest with their rationale. Where a feature is enabled at the member level (`tokio-util = { workspace = true, features = ["rt"] }`), the comment says why this crate opts into that module.

## Dependencies

### Internal

`ganja-permission` — the rules a call is judged by, and the worktree it is judged against. Nothing else, and specifically not `ganja-core`.

### External
